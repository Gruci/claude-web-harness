# dev/LESSONS.md — 사고 연대기 (규칙의 배경)

> 담는 것: 규칙이 생긴 실제 사고 경위와 재작업 대가, 그리고 그 사고를 지금 무엇이 막고 있는지. 담지 않는 것: 규칙 자체(→ `CLAUDE.md` 증거·경계 원칙)·코드 관례(→ `dev/CONVENTIONS.md`). 읽는 시점: 규칙이 과해 보일 때, 그리고 새 사고를 겪어 규칙을 늘릴 때.

`CLAUDE.md`는 매 세션 강제 로드되는 RAM이라 **규칙 요지만** 싣는다. 그 규칙이 왜 생겼는지는 전부 여기에 있다.

**이 파일이 하네스를 키운다.** 사고가 나면 여기 경위를 남기고, 기계로 검사할 수 있으면 `kernel/runner.py`에 게이트를 더한다. 그때부터 그 규칙은 부탁이 아니라 차단이다. 올릴 수 없으면 왜 못 올리는지를 적는다. 지금 게이트는 전부 이 경로로 생겼다 — 설계된 게 아니라 사고마다 하나씩 늘었다.

각 절은 제목 다음 줄에 강제 수단을 선언한다. 선언 누락과 유령 게이트 번호는 검사 29가 잡는다.

```
> 강제: 검사 1·7             기계가 막는다
> 강제: 산문 전용 — <사유>    기계로 못 잡는다. 사유를 반드시 적는다
```

**산문 전용이 많은 것은 정상이자 경고다.** 그 목록이 곧 "아직 사람 규율에만 기대고 있는 구간"이고, 게이트로 올릴 후보 목록이다.

**출처 표기 원칙** — 아래 §1~§12의 경위는 대부분 **원본 프로젝트(fund_monitor) 실증**이다. 이 하네스가 거기서 이식됐기 때문이다. 이 프로젝트 자체 사고가 생기면 해당 절에 덧붙이고 출처를 구분해 적는다. 남의 사고를 이 프로젝트 이력으로 위장하지 않는다.

**삭제 금지** — 여기 서사는 압축·요약 대상이 아니다. 사고 기록이 사라지면 규칙은 근거 없는 잔소리가 되고, 다음 세션이 같은 사고를 반복한다.

## §0 — 절차 생략의 대가

> 강제: 산문 전용 — 절차 준수 여부는 기계가 검출할 수 없다. 스킬과 훅이 유도할 뿐이다

> 규칙 정본: `CLAUDE.md` 4단계 기능 개발 워크플로우
> 출처: 원본 프로젝트 실증 (2026-05-21)

성능 최적화를 research와 plan 없이 바로 구현했다. Cache-Control 미들웨어와 DB 인덱스와 JS 중복호출 제거를 한 번에 밀어붙였다.
결과: 인덱스 설계가 실제 쿼리 패턴과 맞지 않아 통째로 재작업.

**"간단해 보인다"는 판단은 절차 생략의 근거가 되지 않는다. 예외는 오탈자와 1줄 설정값뿐.**

## §1 — 컨텍스트 압축 후 스테일 Read로 편집

> 강제: 산문 전용 — 컨텍스트 압축 경고는 세션 런타임 신호라 정적 검사 대상이 아니다

대화가 길어지면 이전 Read 결과가 요약된다. system-reminder에 **"was read before the last conversation was summarized"**가 뜨면 그 Read는 **무효**다.

- 편집 대상에 stale 경고가 있으면 편집 전 반드시 재Read.
- **"방금 읽은 것 같다"는 느낌은 근거가 아니다.** system-reminder 텍스트가 기준이다.
- 압축 후에는 함수 시그니처와 줄 번호가 바뀌어 있을 수 있다. 추측으로 Edit하면 엉뚱한 줄을 건드린다.

## §2 — "아마 이럴 것이다" 추론으로 주장

> 강제: 산문 전용 — 근거 없는 단언인지는 의미 판정이다

확인 없이 추론해서 단언하는 패턴이다.

- "이 테이블에 데이터가 있을 것이다" → **쿼리로 확인 후** 말한다.
- "이 함수는 X를 반환할 것이다" → **Read 후** 말한다.
- "아마 이 파일일 것이다" → **Glob·Grep 후** 말한다.
- 확인하지 않았으면 "확인이 필요하다"고 명시한다. 추측을 사실처럼 포장하지 않는다.

실사고는 §9와 겹친다. "전종목 합산이라 시장구분이 없다"고 단언했는데 실제로는 차원 테이블에 멀쩡히 있었다.

## §3 — 변경 영향 범위 3-레이어 미추적

> 강제: 산문 전용 — 검사 3·21이 레이어 경계를 막지만 소비자 추적 여부는 검출 불가

의존성 방향은 도메인 패키지 → `db/` → `web/routes/` → `frontend/src/`다.

편집 전 체크리스트:

- `db/reads/` 시그니처나 반환값 변경 → `web/routes/` 호출자 Grep
- `web/routes/` 응답 구조 변경 → `frontend/src/` 소비 훅과 컴포넌트 Grep
- React 컴포넌트·훅·상수 시그니처 변경 → import하는 다른 `.tsx`와 `.ts` Grep
- 배치에서 DB 테이블 구조 변경 → 같은 테이블 읽는 쿼리 전체 Grep

**확인하지 않고 "영향 없을 것이다"라고 판단하는 것은 금지.**

## §4 — "간단해 보인다"로 research·plan 생략

> 강제: 산문 전용 — §0과 같다. 절차 준수는 검출 불가

§0의 반복 위반이다. 추가 기준을 박는다. 아래 중 하나라도 걸리면 research → plan이 필수다.

- 수정 파일이 2개 이상
- 1개 파일이라도 다른 레이어를 호출하거나 다른 레이어에서 호출됨
- "이미 아는 코드다" — 세션 간 변경 가능성이 있어 근거가 안 된다
- 버그 원인이 한 파일에 국한되지 않을 가능성

## §5 — MD 업데이트를 "나중에"로 미룸

> 강제: 검사 11·19·24·25 — MD와 실물이 어긋나면 종료가 막힌다

연쇄 요청이 이어지면 "지금 급한 것 먼저, MD는 나중에" 패턴이 나온다. **나중은 오지 않는다.**

컨텍스트가 압축되면 무엇을 업데이트해야 하는지도 함께 사라진다. 코드 변경이 끝난 **그 턴** 안에 관련 MD까지 끝낸다.

## §6 — 구현 완료 후 plan·research 방치

> 강제: 산문 전용 — 산출물 방치는 검출 가능하나 작업 중 상태와 구분이 안 된다

`docs/tasks/` 루트에 남은 산출물은 다음 세션에서 **"진행 중인 작업"으로 오해된다.**

모든 Todo 체크 직후 그 턴 안에 `git mv`로 `docs/tasks/archive/YYYY-MM-DD-{작업명}/`으로 옮기고 구현 커밋에 포함한다.

## §7 — 규칙을 작성 시점에 안 지켜 사후 리팩토링 유발

> 강제: 검사 1·2·3·6·7 — 400줄·중첩def·읽기쓰기 분리·타입힌트·축약어

> 출처: 원본 프로젝트 실증 (2026-06-01)

코드베이스 전수 점검에서 **규칙 위반 208건**이 나왔다. 타입힌트 149건에 축약어와 400줄 초과와 클로저와 읽기쓰기 혼재가 뒤따랐다. **6단계 대규모 리팩토링 사태**로 번졌다.
규칙 MD는 멀쩡히 있었는데 **코드 작성 시점에 적용되지 않아** 누적된 것이다.

사용자: **"처음부터 규칙 맞춰 짰으면 리팩토링 안 했다. 그럴거면 MD 왜 짰냐."**

이 사고가 작성 시점 훅과 Stop 훅으로 이어지는 모든 자동 게이트의 직접적 원인이다.

작성 시점 셀프체크:

- **기존 파일 이어 붙이기 금지** — 코드를 추가하기 전에 "이 코드의 책임이 이 파일의 단일 책임과 같은가"를 자문한다. 다르면 처음부터 별도 파일을 신설한다. 400줄 게이트는 이 습관의 마지막 방어선이지 분리 기준이 아니다.
- 400줄을 넘으면 그 자리에서 기능 단위 분리. "나중에 분할" 금지.
- 조회는 `db/reads/`, 쓰기는 `db/writes/`. 정본은 `dev/ARCHITECTURE.md`.
- `get_*`는 I/O와 로직으로 쪼갠다. 커넥션이 열린 채 가공하지 않는다.
- 중첩 def 금지. 모듈 함수와 파라미터 전달로 푼다.
- 축약어 금지. 정본은 `dev/NAMING.md`.
- 함수 시그니처에 타입힌트를 단다.

## §8 — 백엔드만 만들고 소비 UI를 안 만듦

> 강제: 산문 전용 — 소비 UI 없는 API를 기계가 고아로 판정할 수 없다

> 출처: 원본 프로젝트 실증 (2026-06-10)

관리자 기능을 레거시 템플릿과 바닐라 JS로 구현했다. 화면은 React SPA가 서빙하므로 **사용자에겐 기능이 통째로 안 보였다.** 뒤늦게 React 포팅으로 복구했다.

사용자: **"내가 코딩할 때 React로 코딩하도록 MD 다 바꿔놓으라고 했지."**

교훈의 핵심은 "레거시를 쓰지 말라"가 아니다. **백엔드만 만들고 소비 UI를 안 만들면 그 기능은 존재하지 않는 것과 같다.** API 라우트를 추가하는 작업은 소비 React 컴포넌트를 같은 작업 안에서 만들어야 완료다.

## §9 — DB 설계 시 확장성과 차원 무시

> 강제: 산문 전용 — 차원 설계의 적절성은 의미 판정이다

> 출처: 원본 프로젝트 실증 (2026-06-24)

DB에는 시간이 지나며 다른 나라와 자산군이 계속 물린다.

사용자: **"db에 데이터 추가될 때마다 설계도 읽고 확장성 고려해서 db 짜라."**

직전 사고: 한 팩트 테이블에만 `market` 컬럼이 빠져 시장 필터가 불가능했다. 그때 "전종목 합산이라 시장구분이 없다"고 잘못 단언했는데, 실제로는 `market`이 종목 차원에 있어야 했다. 설계 실수와 미확인 단언이 겹친 사례다.

- **`dev/DATA_MODEL.md` 먼저 읽는다.** 같은 데이터가 이미 어느 차원에 있는지 확인하고 중복 컬럼을 신설하지 않는다.
- **차원과 팩트를 구분한다.** 불변 속성은 차원 테이블 한 곳, 일별 측정값만 팩트. 팩트마다 차원 컬럼을 denormalize하지 말고 JOIN한다.
- **"나라나 자산군이 하나 더 들어오면?"**을 자문한다. 차원 row 추가만으로 끝나야 정상이다. 팩트마다 컬럼을 추가하는 설계면 틀린 것이다.
- DB 컬럼명도 `dev/NAMING.md`를 따른다. dict 키나 API 필드와 같은 규칙이다.

## §10 — 체계적 디버깅 없이 랜덤 수정

> 강제: 산문 전용 — 디버깅 절차는 검출 불가

**근본 원인 파악 전 수정 시도 금지.** 순서는 넷이다.

1. **근본 원인 조사** — 에러 메시지 완독 → 재현 → 최근 변경 확인 → 데이터 흐름 추적
2. **패턴 분석** — 동작하는 유사 코드를 찾아 차이점을 식별
3. **가설 테스트** — 단일 가설을 최소 변경으로 검증. 실패하면 새 가설. **여러 수정 동시 금지**
4. **구현** — 실패 재현 테스트 작성 → 단일 수정 → 검증

**3회 수정 실패 시 STOP.** 아키텍처 문제를 의심하고 증거와 함께 사용자에게 보고한다.

여러 수정을 동시에 던지면 무엇이 고쳤는지 모르게 된다. 고쳐진 것처럼 보이는 상태가 사실은 다른 걸 깨뜨린 상태일 수 있다.

## §11 — 검증 없이 완료 주장

> 강제: 산문 전용 — 검증 실행 여부는 검출 불가. 훅이 종료를 막을 뿐이다

완료 선언 전 필수 순서는 셋이다. 검증 명령 실행 → 출력 전체 확인 → 출력이 주장을 확인할 때만 선언.

**금지 표현**: "통과할 것이다" / "이제 동작할 것이다" / "수정 완료" / "문제 없어 보인다"

| 주장 | 필요한 증거 | 불충분 |
|------|-----------|--------|
| 테스트 통과 | 테스트 명령 출력에 0 failures | 이전 실행, "될 것" |
| 빌드 성공 | 빌드 명령 exit 0 | 린터 통과 |
| 버그 수정 | 재현 테스트 PASS | "코드 변경함" |

UI 작업은 렌더된 화면을 직접 확인하는 것까지가 검증이다.

## §12 — 공유 체크아웃에서 구현·커밋

> 강제: 산문 전용 — EDITING 잠금 훅이 완료 보고는 강제하나 브랜치 확인 자체는 검출 불가

> 출처: 원본 프로젝트 실증 (2026-07-20)

다른 세션이 공유 트리를 feature 브랜치로 전환해둔 상태에서 **커밋 직전까지 갔다.** 내 커밋이 남의 브랜치에 섞일 뻔했다.

구현과 커밋과 브랜치 조작은 자기 worktree에서만 한다. 공유 체크아웃은 읽기 구역이다.
**첫 편집 전에 현재 브랜치와 경로를 확인하고**, 공유 경로인데 기본 브랜치가 아니면 멈춘다. 정본 절차는 `EDITING.md`다.

## §13 — 게이트를 "실물 생기면 켠다"로 미뤄 래칫이 역전됨

> 강제: 등록 정합 (`check_gate_registry`) — 배선과 설정과 지도의 불일치를 매 실행 대조한다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

게이트 20~26을 "해당 레이어의 실물이 생긴 뒤 켠다"며 OFF로 뒀다. 전부 대상이 없으면 자연 통과하는 설계였고, 실제로 켜보니 전 항목 통과였다. 끌 이유가 처음부터 없었다.

늦게 켜면 그 시점의 위반부터 baseline 면제 목록에 쌓인다. **켤 수 있을 때 켜지 않는 것이 곧 래칫 위배다.** `kernel/gates/tests_pairing.py` 헤더가 그 논리를 이미 적어두고도 정작 자신은 OFF였다.

**대상이 없어 자연 통과하는 게이트는 지금 켠다. 코드가 쌓인 뒤가 아니라.**

## §14 — 파생하지 않은 설정 리터럴이 게이트를 무음 사망시킴

> 강제: 등록 정합 (`DERIVED_PREFIXES` 대조) — 자식 접두사가 부모로 시작하지 않으면 위반
> 출처: 하네스 개발 레포 실증 (2026-08-09)

`READS_PREFIX`가 `DB_PREFIX`에서 파생되지 않고 리터럴이었다. `DB_PREFIX`를 바꾸면 해당 게이트가 대상 0건을 반환한다. 에러가 아니라 **초록불**이다.

더 나쁜 건 그다음이다. 이 버그를 원인으로 오해해 "레이어 이름은 규약이라 바꿀 수 없다"는 규칙을 만들었다. **버그의 증상을 설계 원칙으로 굳힌 것이다.** 파생으로 고치자 그 규칙 자체가 불필요해졌다.

**설정값이 다른 설정값을 함의하면 파생시킨다. 리터럴 복제는 조용히 깨지고, 그 침묵이 잘못된 원칙을 낳는다.**

## §15 — 꺼진 게이트와 배선 빠진 게이트가 화면상 같음

> 강제: 등록 정합 (`check_gate_registry`) — 설정만 있고 배선 없음, 배선했는데 설정 없음을 잡는다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

게이트가 OFF인 것, 배선을 빠뜨린 것, 대상이 없어 통과한 것이 전부 동일하게 보인다. 셋 다 위반 0건이다. 그래서 게이트를 추가하고 배선을 잊어도 아무도 모르고, 검사기가 죽어 있어도 초록불이다.

**"통과"와 "검사하지 않음"을 구분할 수 없는 출력은 검사가 아니다.** 그래서 신규 게이트는 통과 확인만으로 부족하고, 합성 입력으로 실제 발화까지 확인해야 배선된 것으로 본다.

## §16 — 진화 루프를 문서화하지 않아 세션이 루프를 건너뜀

> 강제: 산문 전용 — 지적 발생 자체를 기계가 검출할 수 없다. 검사 29는 절의 강제 표시 누락만 잡는다
> 출처: 하네스 개발 레포 실증 (2026-08-09)

이 하네스의 핵심은 사고를 여기 남기고 검사 가능한 것을 게이트로 올리는 순환이다. 그런데 쓰기(`CLAUDE.md` MD 시냅스)와 읽기(라우팅표)와 승격(일관성 게이트)이 서로 다른 절에 흩어져 있고, **셋을 잇는 문장이 한 줄도 없었다.**

결과: 한 세션에서 하네스 결함 4건을 찾아 전부 게이트로 만들고도 이 파일에는 한 줄도 안 남겼다. 경위는 커밋 메시지로만 갔고, 커밋 메시지는 라우팅표에 없어 다음 세션이 읽지 않는다. §13~§15가 그때 유실될 뻔한 것들이다.

사용자: **"그 레슨을 통해 하네스가 진화한다는 걸 왜 안 적어놓은 거야."**

**시스템의 핵심 동작은 어느 파일에도 안 적혀 있으면 없는 것과 같다.** 파일별 "담는 것"만 적는 서식은 파일 사이에 무엇이 흐르는지를 적게 만들지 않는다. 흐름은 따로 적어야 한다.

## §17 — 관찰 장치 없이 시작해 초기 신호를 잃음

> 강제: 관찰 기록 (`kernel/trace.py`) + 편집 표면 래칫 (`harness_gates/edit_surface.py`)
> 출처: 이 프로젝트 (2026-08-10)

§16 이 잇지 못한 것이 하나 더 있었다. 승격 순환의 **입력**이다.

사고를 `dev/LESSONS.md` 에 남기고 게이트로 올리는 경로는 **사람이 사고를 알아채야** 시작된다. 알아채지 못한 마찰은 그대로 사라진다. 게이트가 걸린 횟수도, 어느 파일에서 반복됐는지도, 어떤 판정이 오탐이었는지도 세션이 끝나면 남지 않는다.

그리고 그 신호가 제일 센 구간이 **하필 프로젝트 초반**이다. 게이트가 제일 많이 걸리고, 관례가 그때 정해지고, 오탐도 그때 드러난다. 코드가 쌓인 뒤에 기록 장치를 붙이면 이미 그 데이터는 없다.

사용자: **"루프를 지금 짜야 하는 이유가 오히려 코드가 없기 때문이다."**

- 훅이 막을 때마다 관찰을 남긴다. 기록 실패가 차단을 막지는 않는다 — 관찰은 차단보다 항상 덜 중요하다.
- 채굴까지가 기계다. **판정은 사람이 한다.** 이 하네스엔 "더 좋아졌다"를 재는 적합도 함수가 없고, 골든 대조는 회귀만 잡지 개선을 못 잰다.
- 적합도 없이 제안과 수용을 자동화하면 루프는 가장 싼 통과 경로로 수렴한다. **면제 목록 늘리기다.** 그래서 편집 표면 래칫이 같은 커밋에 들어갔다. 판정이 수동인 동안에도 그 문을 닫아둬야 나중에 자동화할 여지가 생긴다.
- 거절된 제안은 `dev/REJECTED.md` 에 남긴다. 부정 결과가 사라지면 다음 회고가 같은 제안을 다시 하고, 그 반복이 결국 하나를 통과시킨다.

## §18 — 평가기가 clone 직후부터 반쪽인데 아무도 몰랐음

> 강제: 평가기 자가복구 (`tests/run_golden.py` 가 픽스처 프로파일이 없으면 정본에서 다시 짓는다)
> 출처: 이 프로젝트 (2026-08-10)

폐쇄 루프의 검증 단계로 골든 대조를 재사용하려고 상태를 확인했더니 실패하고 있었다.

원인은 게이트가 아니었다. 픽스처의 `.gitignore` 가 `harness_profile.py` 를 빼고, 그 `.gitignore` 는 바깥 레포에도 적용된다. 즉 픽스처 프로파일은 **한 번도 커밋된 적이 없었다.** clone 하면 파일이 없고, 전 게이트 대조가 프로파일 없는 상태로 돌아 `--bare` 와 똑같은 출력을 낸다.

증상이 고약하다. 실패는 하는데, 화면에 뜨는 것은 "게이트 27건이 통째로 사라졌다"는 diff 다. 그걸 보는 사람은 원인을 게이트에서 찾는다. **평가기가 자기가 반쪽이라고 말하지 않고, 검사 대상이 망가진 것처럼 말한다.**

§15 의 확장이다. 거긴 게이트가 "통과"와 "검사하지 않음"을 구분 못 하는 문제였고, 여기는 평가기가 같은 병에 걸린 경우다. **검사기를 검사하는 것도 검사기이므로, 그쪽이 조용히 죽는 경로도 똑같이 막아야 한다.**

- 평가기가 자기 전제를 못 갖추면 조용히 등급을 낮추지 말고, 다시 갖추거나 그 사실을 말해야 한다.
- 재생성의 정본이 있으면 재생성이 답이다. `tests/fixture_files.py` 가 있는데 파일 하나가 없어서 평가기가 반쪽이 될 이유가 없다.

## 일관성 게이트 — 근본 원인 진단

> 규칙 정본: `CLAUDE.md` 일관성 게이트
> 출처: 원본 프로젝트 사용자 진단 (2026-06-26)

왜 매번 대규모 리팩토링이 터지는가. 원인은 둘이다.

1. **세션마다 새 개발자다.** 매번 컨텍스트 없는 새 Claude가 기능을 붙인다. 각자 제 스타일로 짜니 서비스가 일관되게 확장되지 않고 스파게티가 된다.
2. **MD 규칙은 산문일 뿐 강제가 아니다.** "400줄 지켜라"는 글은 세션이 길어지고 컨텍스트가 압축되면 흘러내린다. **검사 가능한 규칙을 산문으로 단속하려는 것 자체가 실패 메커니즘이다.** MD를 더 써도 안 고쳐진다.

이 진단이 "규칙을 MD에 추가"에서 "**규칙을 `kernel/runner.py`에 추가**"로 방향을 바꾼 근거다. MD는 왜만 적고 강제는 게이트가 한다.

### 래칫 원칙의 실증 근거

> 출처: 원본 프로젝트 전수감사 (2026-07-16)

대규모 정리는 반드시 **그 상태를 잠그는 검사와 같은 커밋**으로 끝낸다. 게이트 없는 정리는 재발한다.
545파일 전수감사 실증: **게이트가 있던 규칙은 위반 0, 산문뿐이던 규칙만 재누적됐다.**
