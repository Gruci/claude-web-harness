# dev/TESTING.md — 테스트 전략 & TDD 규칙

> 담는 것: 어느 계층을 어떻게 테스트하는지, TDD 사이클, 테스트 배치 규칙. 담지 않는 것: 함수 분리 규칙(→ `dev/ARCHITECTURE.md`)·관례 갈림길(→ `dev/CONVENTIONS.md`). 읽는 시점: 테스트를 쓰기 전, 그리고 버그를 고쳐 회귀 방어가 필요할 때.

---

## 0. TDD Iron Law (superpowers 원칙)

```
테스트 없이 프로덕션 코드 작성 금지
```

### RED → GREEN → REFACTOR 사이클

| 단계 | 행동 | 필수 검증 |
|------|------|----------|
| RED | 실패하는 테스트 1개 작성 | `pytest` 실행 → FAIL 확인 (에러가 아닌 실패) |
| GREEN | 테스트를 통과하는 **최소한의** 코드 작성 | `pytest` 실행 → PASS 확인 |
| REFACTOR | 중복 제거·이름 개선 (동작 추가 금지) | `pytest` 실행 → 여전히 PASS |

### TDD 적용 시점

| 시점 | TDD 적용 |
|------|---------|
| 새 기능 구현 | ✅ 필수 |
| 버그 수정 | ✅ 필수 — 재현 테스트 먼저, 수정은 그 다음 |
| 리팩토링 | ✅ 필수 — 기존 테스트 green 유지 |
| 확정된 `_format_*` 함수 | ✅ 필수 |
| 자주 바뀌는 탐색 코드 | ❌ 확정 후 작성 |
| 설정 파일·프로토타입 | ❌ 예외 |

### 합리화 금지

| 핑계 | 현실 |
|------|------|
| "너무 간단해서 테스트 불필요" | 간단한 코드도 깨짐. 테스트 30초면 됨 |
| "나중에 테스트 추가" | 나중에 쓴 테스트는 즉시 통과 → 아무것도 증명 못함 |
| "수동으로 이미 확인" | 기록 없음, 재실행 불가, 회귀 방어 없음 |
| "시간 없어" | TDD가 디버깅보다 빠름 |
| "테스트 어려움 = 설계 문제" | 맞음. 인터페이스 단순화 신호 |

### 테스트 먼저 코드를 썼다면?

**삭제하고 TDD로 다시 시작.** "참고용으로 남기기"도 금지 — 그건 test-after.

## 1. 3-레이어 → 테스트 타입 매핑

`dev/ARCHITECTURE.md`의 계층 구분을 그대로 테스트에 적용한다.

| 레이어 | 함수 패턴 | 테스트 타입 | Mocking | 속도 |
|--------|-----------|-------------|---------|------|
| Logic  | `_format_*()` | Unit | 없음 (순수 함수) | 즉시 |
| I/O    | `_fetch_*()` | Integration | 없음 (Test DB) | 보통 |
| 외부   | 수집 클라이언트 | Mock | HTTP만 (monkeypatch) | 빠름 |
| Public | `get_*()` | (선택적 E2E) | I/O만 제한 | 느림 |

---

## 2. 핵심 규칙

### 2-1. `_format_*`은 반드시 순수 Unit Test
- DB·API 연결 없이 `dict / list` 인자만으로 검증
- 계산 로직(비율·증감·집계)은 **여기서만** 집중 테스트
- 기능 안정화되는 순간 작성 → 이후 리팩터 시 회귀 방어선

### 2-2. Mock at the edges
- **금지**: 프로젝트 내부 모듈 간 Mocking (`_fetch_*`를 mock 해서 `get_*` 테스트 등)
- **허용**: 외부 HTTP, 시스템 시각 (`datetime.now`)
- 외부 HTTP는 `monkeypatch`로 클라이언트 함수를 스텁하는 방식이 정본

### 2-3. 앱 레벨 테스트는 `TestClient` 사용
- `tests/conftest.py`의 세션 픽스처가 테스트용 DATABASE_URL·더미 시크릿을 주입하고 `TestClient(app, raise_server_exceptions=False)`로 앱 전체를 노출
- 초기에는 **DB 미의존 경로(라우팅·인증·파서)** 위주로 시작

### 2-4. Fixtures는 `tests/fixtures/`에 보관
- 외부 응답 파싱이 있으면 **실제 응답 픽스처**(HTML/JSON)를 저장 — 파서 회귀 방어선
- 같은 데이터를 여러 테스트가 재사용 → 코드 중복 방지

---

## 3. 배치 규칙

| 경로 | 무엇이 들어가나 |
|------|---------------|
| `tests/conftest.py` | 세션 TestClient와 공용 픽스처 |
| `tests/fixtures/` | 정적 응답 픽스처. 검사기 대상에서 제외된다 |
| `tests/test_*.py` | 초기에는 flat으로 둔다 |
| `tests/unit/` | 순수 함수 unit. 테스트가 늘면 여기로 분리한다 |

---

## 4. 실행

```bash
python -m pytest tests/ -x -q      # 전체 (빠른 것 위주)
python -m pytest tests/unit/ -v    # unit만
```

## 5. 좋은 테스트 기준

| 품질 | Good | Bad |
|------|------|-----|
| Minimal | 하나만 테스트. 이름에 "and" 있으면 분리 | `test_validates_email_and_domain_and_whitespace` |
| Clear | 이름이 동작을 서술 | `test_test1` |
| Real | 실제 코드 경로 검증 | mock 동작만 검증 |
| Intent | 원하는 API를 보여줌 | 구현 세부사항에 결합 |

## 6. 검증 체크리스트 (완료 전 필수)

- [ ] 모든 새 함수/메서드에 테스트 있음
- [ ] 각 테스트가 실패하는 걸 확인한 후 구현함
- [ ] 최소한의 코드만 작성해서 통과시킴

- [ ] 출력에 에러/경고 없음

- [ ] 엣지 케이스·에러 케이스 커버
