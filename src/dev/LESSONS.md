# LESSONS.md — 사고 연대기 (규칙의 배경)

> 담는 것: 규칙이 생긴 실제 사고 경위 — 날짜·인용·재작업 대가. 담지 않는 것: 규칙 자체(→ `CLAUDE.md` 실수 패턴·`dev/CONVENTIONS.md`). 읽는 시점: 규칙이 과해 보이거나 "이번은 예외 아닌가" 싶을 때.
>
> **이 파일의 역할**: 세션 진입점(`CLAUDE.md`·`AGENTS.md`)은 매번 강제 로드되는 RAM이라 **규칙
> 요지만** 싣는다. 그 규칙이 왜 생겼는지 — 실제 사고 경위·날짜·사용자 인용 — 은 전부 여기에 있다.
> **Claude·Codex 공용 사고 기록**이다 — 어느 하네스로 들어왔든 규칙에 이의를 제기하기 전엔 여길 읽는다.
> **읽어야 할 때**: 규칙이 과해 보이거나 "이번은 예외 아닌가" 싶을 때. 대부분의 규칙은 이미 한 번
> 대가를 치르고 생겼다. 이의 제기 전 해당 절을 읽고, 그래도 바꿔야겠으면 사용자에게 묻는다.
>
> **삭제 금지 원칙**: 여기 있는 서사는 압축·요약 대상이 아니다. 사고 기록이 사라지면 규칙은
> 근거 없는 잔소리가 되고, 다음 세션이 같은 사고를 반복한다.

## 실수 패턴 배경 서사 (§1~§14)

> 원 맥락: 이 프로젝트는 KOFIA·ETF·뉴스·경영공시·매크로·산업사이클·애널리스트·시황·전자공시·본부이슈·웹·배치 등
> 여러 도메인이 3-레이어로 얽혀 있다. 세션이 길어질수록, 코드가 익숙해질수록 아래 실수가 반복된다.
> **각 체크포인트는 "생략 가능" 판단이 아니라 강제 실행이다.**

### §1 — 컨텍스트 압축 후 스테일 Read로 편집

> 규칙 정본: `CLAUDE.md` 실수 패턴 1

대화가 길어지면 이전 Read 결과가 요약(압축)된다.
system-reminder에 **"was read before the last conversation was summarized"** 라고 뜨면 그 Read는 **무효**다.

- 편집 대상 파일에 stale Read 경고가 있으면 **편집 전 반드시 재Read**.
- **"방금 읽은 것 같다"는 느낌은 근거가 아니다. system-reminder 텍스트가 기준이다.**
- 세션이 압축되면 함수 시그니처·줄 번호가 바뀌어 있을 수 있다. 추측으로 Edit하면 엉뚱한 줄을 건드린다.

### §2 — "아마 이럴 것이다" 추론으로 주장

> 규칙 정본: `CLAUDE.md` 실수 패턴 2

DB 상태·함수 동작·파일 경로를 확인 없이 추론해서 단언하는 패턴.

- "이 테이블에 데이터가 있을 것이다" → **쿼리로 확인 후 말할 것**.
- "이 함수는 X를 반환할 것이다" → **Read로 읽은 후 말할 것**.
- "아마 이 파일일 것이다" → **Glob/Grep으로 확인 후 말할 것**.
- 확인하지 않았으면 "확인이 필요하다"고 명시. **추측을 사실처럼 포장 금지.**

관련 실사고는 §9(“전종목 합산이라 시장구분 없다”고 잘못 단언) 참조.

### §3 — 변경 영향 범위 3-레이어 미추적

> 규칙 정본: `CLAUDE.md` 실수 패턴 3

의존성 방향: `kofia/` → `db/` → `web/routes/` (API) → `frontend/src/` (React 소비)

편집 전 체크리스트 전문:
- `db/reads/` 함수 시그니처·반환값 변경 → `web/routes/` 호출자 Grep 확인
- `web/routes/` API 응답 구조 변경 → `frontend/src/` `useApi`/fetch 호출부 Grep 확인 (소비 컴포넌트·훅)
- React 컴포넌트/훅/상수 시그니처 변경 → 같은 모듈을 import하는 다른 `frontend/src/*.tsx`/`*.ts` Grep 확인
- 배치 스크립트에서 DB 테이블 구조 변경 → 같은 테이블 읽는 쿼리 전체 Grep 확인

**확인하지 않고 "영향 없을 것이다"라고 판단하는 것은 금지.**

> 이미 4단계 워크플로우에 기록되어 있으나 **반복 위반됨** (2026-05-21 사례 — 이 파일 상단 참조).
> 여기에 추가 기준을 박는다.

research → plan 필수 조건(하나라도 해당 시):
- 수정 파일이 2개 이상

- "이미 아는 코드다" — 세션 간 코드가 변경되었을 수 있으므로 근거 안 됨
- 버그 수정이라도 원인이 한 파일에 국한되지 않을 가능성이 있으면

**"1줄 변경인데 research가 필요하냐"는 자문은 생략 근거가 아니다. 오탈자·설정값 1줄만 예외.**

### §5 — MD 업데이트를 "나중에"로 미룸

> 규칙 정본: `CLAUDE.md` 실수 패턴 5

연쇄 요청이 이어지면 "지금 당장 중요한 거 먼저, MD는 나중에" 패턴이 나온다.
**나중은 오지 않는다.**

- 코드 변경이 완료된 **그 턴** 안에 관련 MD 업데이트까지 끝낸다.
- "다음 세션에서 업데이트하겠다"는 계획은 없는 것과 같다. **컨텍스트가 압축되면 무엇을 업데이트해야 하는지도 사라진다.**

### §6 — 구현 완료 후 plan/research 방치

> 규칙 정본: `CLAUDE.md` 실수 패턴 6

구현이 끝나면 "다음 작업이 급하니 archive는 나중에" 패턴이 나온다.
docs/tasks/ 루트에 남은 파일은 **다음 세션에서 "진행 중인 작업"으로 오해된다.**

- 모든 Todo 체크 완료 직후 **그 턴 안에** `git mv docs/tasks/plan.md docs/tasks/archive/YYYY-MM-DD-{작업명}/plan.md` 실행
- research.md도 동일하게 이동
- 이동을 구현 커밋에 포함하거나 별도 커밋으로 즉시 처리
- docs/tasks/ 루트에 plan.md / research.md 가 남아 있으면 → 미완료 작업이 있다는 신호

### §7 — 규칙을 "작성 시점"에 안 지켜 사후 리팩토링 유발 ★

> 규칙 정본: `CLAUDE.md` 실수 패턴 7

> **2026-06-01**: 코드베이스 전수 점검에서 **208건 규칙 위반**(타입힌트 149·축약어·400줄·클로저·SSL중복·읽기쓰기 혼재)
> 발견 → **6단계 대규모 리팩토링 사태**.
> MD 규칙(ARCHITECTURE/NAMING)이 멀쩡히 있었는데 **코드 작성 시점에 적용 안 해** 누적됨.
> 사용자: **"처음부터 규칙 맞춰 짰으면 리팩토링 안 했다. 그럴거면 MD 왜 짰냐."**

이 사고가 뒤에 이어지는 모든 자동 게이트(작성시점 훅 + Stop 훅)의 직접적 원인이다 — 아래 "일관성 게이트 근본 원인 진단" 참조.

세부 규칙 원문(요지는 CLAUDE.md에 잔류):
- **기존 파일 이어 붙이기 금지 (2026-07-20 harnes 역이식)** — 코드를 추가하기 **전에** "이 코드의 책임이 이 파일의 단일 책임과 같은가?" 자문. 다르면 처음부터 별도 파일/모듈 신설. "기존 파일에 추가"는 기본값이 아니다 — 400줄 게이트는 이 습관의 마지막 방어선이지 분리 기준이 아니다.
- **400줄 이하** — 넘으면 그 자리에서 기능 단위 분리. "나중에 분할" 금지.
- **DB 조회 = `db/reads/`, 쓰기(INSERT/UPDATE/DELETE) = `db/writes/`** — 한 파일·함수에 섞지 말 것 (정본: `dev/ARCHITECTURE.md`)
- **`get_*`는 `_fetch_*`(I/O)·`_format_*`(로직) 분리**, 커넥션 열린 채 가공 금지
- **중첩 def(클로저) 금지** → 모듈 함수 + 파라미터 전달
- **축약어 금지**(rev/oper/net/nr/oi 등) → 풀네임
- **함수 시그니처 타입힌트**(파라미터·반환)

새 파일/함수 만들 때 "읽기냐 쓰기냐 · 400줄 넘냐 · 레이어 맞냐 · 타입힌트 있냐"를 **먼저** 자문하고 작성한다.

### §8 — 프론트 신규 기능을 레거시(Jinja/바닐라JS)로 구현 ★

> 규칙 정본: `CLAUDE.md` 실수 패턴 8

> **2026-06-10**: ETF 테마 클러스터/규칙 관리자를 **레거시 `web/admin/templates/` + `web/static/admin/` 바닐라 JS** 로 구현함.
> React SPA(`/admin`)가 화면을 서빙하므로 **사용자에겐 기능이 통째로 안 보임**(orphan 백엔드). 뒤늦게 React 포팅으로 복구.
> 사용자: **"내가 코딩할 때 React 로 코딩하도록 MD 다 바꿔놓으라고 했지."**

교훈의 핵심은 "레거시 파일을 쓰지 말라"가 아니라 **"백엔드만 만들고 소비 UI를 안 만들면 기능은 존재하지 않는 것과 같다"**
— API 라우트를 추가하는 작업은 소비 React 컴포넌트를 **같은 작업 안에서** 만들어야 완료다.

### §9 — DB 설계 시 확장성/차원 무시 (단기 설계) ★

> 규칙 정본: `CLAUDE.md` 실수 패턴 9

> **2026-06-24**: 이 DB는 점점 다른 나라·자산군(KR 증시 → 미국 NASDAQ/NYSE → …)이 물린다.
> 사용자: **"db에 데이터 추가될 때마다 설계도(DATA_MODEL.md) 읽고 확장성/사용성 고려해서 db 짜라."**
> 직전 사고: `equity_short`만 `market` 컬럼이 빠져 시장 필터 불가 → **"전종목 합산이라 시장구분 없다"고 잘못 단언**.
> 실제론 `market`이 종목 차원(`stock_master`)에 있어야 했고, movers는 컬럼이 멀쩡히 있었는데 안 쓰고 있던 것.

즉 이 사고는 설계 실수(§9)와 미확인 단언(§2)이 겹친 사례다 — 없다고 단언하기 전에 차원 테이블을 먼저 봤어야 했다.

세부 규칙 원문:
- **`dev/DATA_MODEL.md` 먼저 읽는다**(설계도). 같은 데이터가 이미 어느 차원/테이블에 있는지 확인 — 중복 컬럼 신설 금지.
- **차원 vs 팩트 구분**: 종목의 불변 속성(market·country·섹터·이름)은 차원(`stock_master`) 한 곳. 일별 측정값만 팩트. **팩트마다 market 컬럼 denormalize 금지 → JOIN.**
- **"나라/자산군 하나 더 들어오면?"** 자문 — 차원 row 추가만으로 끝나야 정상. 팩트마다 컬럼 추가 설계면 틀린 것.
- **컬럼 네이밍**: `dev/NAMING.md`(의미 기반·축약 금지·내부코드 금지) — DB 컬럼도 dict 키·API 필드와 동일.
- 정본 절차·원칙: `dev/DATA_MODEL.md` 상단 "DB 설계 표준 절차" + "종목 차원-팩트 설계 원칙".

### §10 — 체계적 디버깅 없이 랜덤 수정

> 규칙 정본: `CLAUDE.md` 실수 패턴 10 (2026-07-20 harnes 역이식)

**근본 원인 파악 전 수정 시도 금지.** 4단계 순서 전문:

1. **근본 원인 조사**: 에러 메시지 완독 → 재현 → 최근 변경 확인 → 데이터 흐름 추적
2. **패턴 분석**: 동작하는 유사 코드 찾기 → 차이점 식별
3. **가설 테스트**: 단일 가설 → 최소 변경으로 검증 → 실패 시 새 가설 (**여러 수정 동시 금지**)
4. **구현**: 실패 재현 테스트 작성 → 단일 수정 → 검증

**3회 수정 실패 시 STOP** → 아키텍처 문제 의심, 사용자에게 보고.
(여러 수정을 동시에 던지면 무엇이 고쳤는지 모르게 되고, 고쳐진 것처럼 보이는 상태가 사실은 다른 걸 깨뜨린 상태일 수 있다.)

### §11 — 검증 없이 완료 주장

> 규칙 정본: `CLAUDE.md` 실수 패턴 11 (2026-07-20 harnes 역이식)

완료 선언 전 필수: ① 검증 명령 실행(`pytest`, `npx tsc`, `npm run build`, `python static_check.py` 등)
② 출력 전체 확인(exit code + 에러/경고 수) ③ **출력이 주장을 확인할 때만** 선언.

**금지 표현 (검증 전):** "통과할 것이다" / "이제 동작할 것이다" / "수정 완료" / "문제 없어 보인다"

증거 표 전문:

| 주장 | 필요한 증거 | 불충분 |
|------|-----------|--------|
| 테스트 통과 | 테스트 명령 출력: 0 failures | 이전 실행, "될 것" |
| 빌드 성공 | 빌드 명령: exit 0 | 린터 통과 |
| 버그 수정 | 재현 테스트 PASS | "코드 변경함" |

UI 작업은 렌더 화면 직접 확인까지 (Orca 브라우저 — `memory/feedback_visual_verification.md`).

### §13 — 기준일에 안 묶인 조회는 조용히 낡는다 (LLM 이 그 위에 인과를 짓는다)

> 규칙 정본: `CLAUDE.md` 증거·경계 원칙 1. 도메인 계약: `market_briefing/MARKET_BRIEFING.md` 시장 실측치

> **실사고**: 브리핑 실측치 중 지수·수급만 `data_date` 에 묶여 있고 채권·환율 스냅샷은 인자가 없어
> "DB 의 최신 행"을 집었다. 매크로 배치가 브리핑보다 늦게 도는 구조라 **상시 하루 이상 낡은 값**이
> 기준일 값으로 실렸고, 이틀 연속 같은 금리·환율이 나가도 아무도 몰랐다.

- **LLM 생성 배치는 수집이 전부 끝난 뒤 맨 마지막이다.** 데이터를 근거로 프롬프팅하는 물건이 수집기보다 먼저 돌면 무슨 짓을 해도 낡은 입력을 읽는다. 수집 창(저녁~새벽)과 생성 시각(아침)을 분리하고, 생성물이 읽는 모든 수집기가 그 앞에 있는지 확인한다. (2026-07-29 사용자 지시)
- 같은 블록을 조립하는 조회는 **전부 같은 기준일 인자를 받아야 한다.** 하나만 인자가 없으면 그 하나가 틀린다.
- 그래도 외부 공표가 늦어 정합을 못 맞추는 구간은 값을 지우지 말고 **관측일을 노출**한다. 빈칸은 정보 손실이고, 라벨 없는 옛 값은 오보다.
- 사용자 지적은 문체였지만("~풀이된다"), 같은 산출물에서 더 심각한 수치 오류가 나왔다. **문체 불평이 들어오면 그 문단의 숫자부터 대조한다.**
- 나는 이 상황을 처음에 "매크로를 당기면 FRED 가 낡는다"로 정리해 스케줄 조정을 기각했다 — **질문을 반대로 잡은 것**이다. 소비자를 뒤로 미는 선택지를 아예 안 봤다.

### §14 — 프롬프트에 규칙을 더하면 문체가 딸려 온다

> 규칙 정본: `market_briefing/MARKET_BRIEFING.md` 프롬프트 변경 = 골든셋 게이트

> **실사고**: "관찰에는 원인 가설 1문장"(V0.4)을 넣자 다음 산출물에서 전언·추정 종결
> ("~로 풀이된다"·"~는 평가가 나온다")이 배로 늘었다. 한국어에서 가설의 기본 종결형이 그것이다.

- 새 규칙은 **내용만이 아니라 문형도 지시한다.** 원하는 문장 형태의 예시를 함께 박지 않으면 모델이 입력 코퍼스의 문체(여기선 신문 기사체)로 회귀한다.
- 사외로 나갈 수 있는 문서에서 "평가가 나온다"류 무주체 전언은 **화자가 사라진 문장**이다 — 주장의 주체를 반드시 남긴다.

### §15 — 낡은 백로그는 없는 백로그보다 위험하다

> 규칙 정본: `HARNESS.md` 훅 ① `.claude/hooks/git_staleness.py`

> **실사고**: "백로그 뭐 남았냐"에 공유 체크아웃의 `EDITING.md` 를 읽고 정리 과업 plan 을 세워
> Fable 검토까지 받았다. worktree 를 파고 첫 grep 에서 드러났다 — origin/main 이 **9커밋 앞서 있었고
> 계획한 5건 중 4건이 이미 머지돼 있었다.** 리서치·plan·검토가 통째로 낭비됐다.

- 공유 체크아웃은 아무도 pull 하지 않으면 계속 뒤처진다. **읽기 전용 구역이라는 성격이 갱신 면제를 뜻하지 않는다.**
- 갱신된 백로그가 내 계획보다 정확했다. 남은 1건에 대해 그쪽은 git 이력 실측("그 이름이 main 에 있던 시간은 4분")을 담고 있었고, 그걸 못 본 내 답은 서버에 **중복 인덱스를 만들 악수**였다.
- **Fable 검토는 전제의 신선도를 보증하지 않는다.** 내가 준 전제가 낡으면 검토도 같이 낡는다.
- 이 규칙을 메모리 문장으로 적었다가 되돌렸다 — 검사 가능한 규칙이라 훅이 정답이다(일관성 게이트 ①). 자동 정렬의 dirty 판정도 자체 구현을 버리고 `git pull --ff-only` 에 맡겼다: 상시 변경되는 tracked 파일 하나 때문에 자체 검사는 영영 안 탄다.

### §16 — 프롬프트 분량은 실행 예산도 먹는다

> 규칙 정본: `market_briefing/MARKET_BRIEFING.md` claude -p 호출 계약

> **실사고**: 프롬프트 V1.0(§14 의 수정판)을 넣은 다음 첫 평일 아침, 시황 보고서가 안 나왔다.
> `_TIMEOUT_SEC = 300` 에 정확히 걸린 `TimeoutExpired` 였다. 늘린 것은 품질 규칙이었지만
> 같이 늘어난 것은 **생성 시간**이었다. 전날 V0.4 는 같은 300초 안에 끝났다.

- 프롬프트 리뷰는 산출물의 **내용**만 본다. 요구 분량이 실행 예산을 넘겼는지는 산출물에 안 나타난다 — 그날 보고서가 그냥 없다.
- 실패가 self-heal 로 덮여 더 조용해진다. 다음 배치가 소급하지만 원인이 그대로면 매일 같은 자리에서 타임아웃을 다시 태운다. **자가복구는 원인 수정이 아니다.**
- 진단이 한 번의 왕복으로 끝난 건 예외 문구가 갈라져 있었기 때문이다(타임아웃/파싱/빈 필드). 반면 **소요 시간을 안 남긴 탓에 올릴 값은 실측 없이 추정해야 했다** — 한도에 걸릴 수 있는 호출은 소요/한도를 같이 찍는다.

### §17 — 프론트와 백엔드는 같은 배포에서 함께 갱신되지 않는다 ★

> 규칙 정본: 게이트 ⑮ (`static_check_api_types.py`)

> **실사고 2회, 같은 날**: 응답에 새 필드를 더하면서 프론트가 그 필드를 바로 썼다.
> 배포 후 번들은 새것인데 서버 파이썬이 아직 옛 코드라 필드가 **undefined 로 도착**했다.
> 1회차(`board_order`)는 빈 목록을 순회해 **보드 블록이 전멸**했고, 2회차(`asset_groups`)는
> `.find()` 가 undefined 를 읽어 **런타임 크래시로 화면이 백지**가 됐다. 사용자가 콘솔 에러를
> 붙여 줄 때까지 몰랐다.

- **로컬에서는 절대 재현되지 않는다.** 로컬은 서버를 재기동하니 백엔드가 항상 새 코드다. tsc·build·게이트·렌더 확인이 전부 통과하고도 배포에서만 터진다 — 검증 통과가 안전을 뜻하지 않는 구간이다.
- 1회차를 겪고 폴백까지 넣은 뒤 **2회차를 같은 방식으로 냈다.** "다음엔 조심"이 안 통한다는 증거다. 산문 규칙으로 남겼으면 세 번째가 있었다.
- 두 실패 양상이 다르다는 게 함정이다. 순서 폴백은 조용히 비고, 무방비 메서드 호출은 화면을 통째로 죽인다. **후자가 더 낫다** — 조용한 쪽은 며칠 안 들킨다.
- 게이트는 **선언부만** 본다. 소비처를 정적으로 훑으면 로컬 변수까지 걸려 오탐이 43건 나왔다. 타입을 옵셔널로 강제하면 **tsc 가 소비처 전부를 대신 잡는다** — 검사 한 줄이 타입체커를 부리는 구조가 정적 분석을 늘리는 것보다 정확하다.
- 기존 49건은 baseline 동결이다. 되돌아보면 **그 49건도 같은 폭탄**이지만, 전부 고치는 것과 새 폭탄을 막는 것 중 후자가 먼저다(래칫).

### §18 — 불변식을 세워도 마지막 한 곳이 그 불변식을 우회하면 사용자에겐 전부 거짓이다

> 규칙 정본: `db/DB.md` ⛔ bare 최신일 금지 · 게이트 ⑱ (`static_check_complete_date.py`)

> **실사고**: KOFIA 배치가 동시성 문제로 중간에 죽어 2026-07-31 은 ETF 2종만 적재됐다.
> 데이터 엔드포인트 전부가 완전일 resolve(`get_latest_complete_date`)를 타도록 이미 정비돼

> 그 값을 그대로 보여 미수집일이 전 화면의 기준일 라벨로 노출됐다. 사용자가 admin 수집
> 현황과 대조해 잡았다 — "숫자가 다 크롤링 된 다음에 뿌리라"는 기지시의 재발이다.

- 불변식 정비는 **소비처 전수 마감까지가 한 단위다.** N-1 곳을 고치고 1곳을 남기면 사용자 눈에는 아무것도 안 고친 것과 같다 — 기준일 라벨은 화면에서 가장 눈에 띄는 숫자다.
- DB.md 에 ⛔ 산문 금지가 이미 있었지만 이 재발을 못 막았다. **산문 규칙은 기존 코드를 소급 검사하지 않는다** — 금지를 적은 그 턴에 grep 전수 + 게이트化까지 가야 마감이다(일관성 게이트 원칙의 재확인).
- 메타/헬스체크류 엔드포인트는 "데이터가 아니다"라는 이유로 정비 스코프에서 빠지기 쉽다. **기준일을 반환하면 그것도 데이터 엔드포인트다.**

## 15. 저장 타입이 소스 정밀도를 못 담으면 파이프라인 전체가 조용히 틀린다 (2026-07-30)

사용자 신고는 "`/industry` 엑셀이 백만원 단위로 올림돼 받아진다"였다. 엑셀 생성부터 라우트·읽기 쿼리까지
전 경로를 훑었지만 **반올림하는 코드는 어디에도 없었다**. DB 가 이미 잘린 값을 들고 있었다.

`kofia_data`·`kofia_agg` 금액 20컬럼이 `REAL`(float4)이었다. 가수 24비트라 2^24 초과 정수를 표현하지 못한다.
KOFIA 는 1원 단위 정수(`168,888,472,655`)를 주는데 DB 엔 유효 8자리(`2.0281646e+15`)로 스냅돼 들어갔다.

**엑셀만의 문제가 아니었다.** 같은 값을 화면 수치·CAGR·예측·브리핑이 전부 쓰고 있었다. 조·억으로 표시되는
화면에서는 눈에 띄지 않아 수년간 아무도 몰랐다 — **표시 단위가 굵으면 저장 정밀도 손실은 증상을 감춘다.**

### 왜 조기에 못 잡았나

수집·저장·읽기 어디에도 버그가 없다. 각 레이어는 받은 값을 성실히 넘긴다. 결함은 **컬럼 선언 한 줄**에 있었고,
그건 코드 리뷰에서 "REAL 이면 실수형이니까 금액에 맞다"로 통과하기 딱 좋은 형태다. float4 의 정수 표현
한계(2^24)를 그 자리에서 떠올려야만 잡히는데, 사람이 매번 그러기를 기대하는 게 실패 지점이었다.

### 규칙이 아니라 게이트로

산문으로 "금액에 REAL 쓰지 마라"를 적는 것은 §14 가 이미 실패로 판정한 방식이다. 그래서 게이트 ⑭
(`static_check_schema.py`)를 **타입 교정과 같은 커밋에** 넣었다(래칫 원칙). `REAL` 선언을 금지하고,
`NUMERIC(p,s)` 의 소수 스케일에는 소스 정밀도 근거 주석을 요구한다 — 후자는 문구를 검사하는 게 아니라
**스케일을 정하기 전에 소스를 확인하게 만드는 것**이 목적이다(`# any-ok: 사유` 와 같은 계약).

같은 감사로 `us_fundamentals.shares_short`(REAL·주식수)와 `etf_pdf.contracts`(`NUMERIC(18,1)`·소스는
소수 2자리)도 같은 병으로 드러났다. **한 건을 잡으면 동종을 전수로 훑는다.**

### 교체(swap)를 피하고 확대(ALTER)를 택한 이유

이미 잘린 과거 값은 타입 확대로 복구되지 않아 전량 재수집이 필요한데, 운영 DB 의 UPSERT 부담을 피하려고
"로컬 재수집 → 테이블 원자 교체"를 설계했었다. Fable 다중 렌즈 감사가 **BLOCKER 를 잡았다**:
`기업성장` 이 나중에 `ALTER TABLE ADD COLUMN` 으로 붙어 라이브에선 마지막 컬럼(27번)인데
`db/schema_core.py` DDL 은 중간(22번)에 선언한다. DDL 로 만든 스테이징에 `INSERT ... SELECT *` 를 하면
6개 컬럼이 한 칸씩 밀리고, **전부 같은 타입이라 에러도 안 난다** — 740만 행 무성 오염이었다.

교훈은 두 가지다.

1. **DDL 문자열과 실제 테이블의 물리 컬럼 순서는 갈라진다.** `ADD COLUMN` 은 끝에 붙지만 DDL 은 보기 좋은
   자리에 끼워 넣기 때문이다. 위치 기반 `SELECT *` 복사는 이 갈라짐 위에서 조용히 틀린다. **명시 컬럼 목록만 쓴다.**
2. **실패 모드의 종류로 고른다.** 확대 변환의 최악은 "느려짐·디스크 참" 으로 눈에 보이고 되돌릴 수 있다.
   교체의 최악은 "조용히 틀린 값" 으로 발견이 늦고 백업 복원뿐이다. **한정·가시·복구가능한 비용**을
   **무한·무성·복구불가한 위험**보다 택한다. 단계가 적은 쪽이 아니라.

### §19 — "CI 통과 확인"은 파이프라인 exit code 가 아니라 판정 출력으로 한다

> 규칙 정본: `EDITING.md` worktree 프로토콜 4(완료: CI 통과 확인 → merge)

> **실사고**: refactor_audit PR#303 에서 `gh pr checks --watch ... | tail -2 && gh pr merge` 로
> 체인했다. watch 가 네트워크 EOF 로 죽었지만 파이프 마지막 명령(tail)의 exit 0 이 체인을 통과시켜
> **checks 가 pending 인 채로 merge 가 나갔다.** 사후 run watch 로 통과를 확인해 실해는 없었지만,
> 실패였다면 배포 트리거(merge)가 깨진 코드를 서버로 보냈다.

- 파이프(`|`)의 exit code 는 마지막 명령 것이다 — 판정 명령을 파이프에 넣는 순간 판정이 사라진다.
- CI 대기는 `gh run watch <id> --exit-status` 를 **단독 실행**하고, merge 는 그 성공을 눈으로 본 **다음
  호출**로 분리한다. 대기와 실행을 한 체인에 넣지 않는다.
- "merge 됐으니 통과였겠지"는 역산이다 — 이 레포의 checks 는 branch protection 필수 체크가 아니라서
  pending 머지가 실제로 가능하다.

### §20 — 결정을 요청할 때 내부 용어로 물으면 그것은 질문이 아니다 ★

> 규칙 정본: `CLAUDE.md` 0단계 범위 인터뷰

> **실사고**: 백로그 🟡 항목을 처리하며 "pg_hba `trust` 를 잠글까" · "E1 소스 레지스트리화를
> 당길까" 로 AskUserQuestion 을 띄웠다. 사용자 답은 **"pg_hba가 뭔데 씨팔"** · **"이것도 뭔소린지
> 이해가 안간다"** 였다. 선택지 설명이 전부 코드 관점 서술(스크립트 13곳·fetch 시그니처 wrapper)이라
> 무엇을 고르든 무엇이 달라지는지가 안 담겼다.

- **백로그 항목명은 나에게 붙인 라벨이지 사용자에게 던질 질문이 아니다.** 항목명을 그대로 질문에
  넣는 순간 사용자는 그 이름의 뜻부터 역추적해야 한다.
- 결정 질문에 반드시 담을 4가지: **① 이게 뭔지 · ② 왜 지금 문제로 올라왔는지 · ③ 이걸 골랐을 때
  실제로 뭐가 좋아지는지 · ④ 대신 뭘 잃는지.** 넷 중 하나라도 비면 질문이 아니라 통보다.
- 손익은 **사용자가 겪는 층**으로 번역한다. "스크립트 13곳 수정"이 아니라 "실패하면 배포와 백업이
  동시에 죽는다", "레지스트리화"가 아니라 "화면은 안 바뀌고 다음에 소스 붙일 때만 편해진다".
- 화면에 아무 변화가 없는 내부 정리는 **그 사실 자체를 먼저** 말한다. 사용자가 기대할 산출물이
  없다는 게 판단에 가장 큰 정보다.
- 이 규칙은 `AskUserQuestion` 뿐 아니라 plan 의 트레이드오프 절과 백로그 우선순위 제안에도 같이 건다.
