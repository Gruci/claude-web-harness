## 4단계 기능 개발 워크플로우

**모든 기능 추가·수정·버그 수정은 아래 순서대로.** 단순 오탈자와 설정값 1줄 변경만 예외다.

**0** 범위 인터뷰 → **1** 리서치 → **2** 계획 → **2-1** 검토·반복 — **여기까지 코드 수정 금지** → **3** 구현 → **4** 수정·롤백. **3단계부터만 코드를 만진다.**

- **0단계 범위 인터뷰**: 리서치 전에 결정 지점을 AskUserQuestion으로 먼저 묻는다. 스코프 경계·데이터 적재 방식·화면 노출 위치처럼 답에 따라 결과물이 달라지는 것들이다.
- **브리프 패스트트랙**: 요청에 스코프·노출 위치·적재 방식 3요소가 이미 담겼으면 인터뷰를 생략하고 바로 리서치로 간다. 다 갖춘 요청에 형식적으로 되묻는 것은 절차 준수가 아니라 지연이다.
- **이견 병기**: 사용자 지시가 내 기술 판단과 다르면 지시대로 이행하되 착수 시점에 "이견 1줄 / 근거 1줄"을 명시한다. 이견이 없으면 침묵한다. 설계를 바꿔야 할 수준이면 먼저 묻는다.
- 1~2단계 산출물은 `docs/tasks/research_<과업>.md`와 `plan_<과업>.md`다. 채팅창 요약 금지, 파일로 남긴다. 병행 세션 가능성이 있으면 과업 접미 파일명을 쓴다.
- **plan 승인 전 구현 절대 금지.** 승인 후에는 완료까지 잠금·코드 수정·MD 갱신·archive 이동을 중간 확인 없이 처리하고 결과만 보고한다.
- 구현 완료 즉시 같은 턴에 `docs/tasks/archive/YYYY-MM-DD-{작업명}/`으로 `git mv`한다. "나중에 정리"는 오지 않는다.
- **"깃에 올려라" = push → PR 생성 → CI 통과 → merge → 보드 행 제거**까지 한 번에다. main 직푸시는 폐기됐고 배포는 merge가 트리거다.
- Why: plan 없이 최적화를 직행했다가 인덱스가 실제 쿼리 패턴과 안 맞아 재작업했다. `dev/LESSONS.md` §4.

## 증거·경계 원칙

> 사고 경위 정본은 `dev/LESSONS.md`다. 규칙이 과해 보이면 먼저 읽는다.

1. **주장엔 외부 증거** — DB 상태는 쿼리로, 함수 동작은 Read로, 파일 존재는 Glob·Grep으로 확인한 뒤 말한다. 미확인이면 "확인이 필요하다"고 명시한다. §2
2. **완료 선언은 검증 출력과 함께** — `pytest`·`npx tsc`·`npm run build`·`python static_check.py` 출력이 주장을 확인할 때만 선언한다. UI는 렌더 화면까지 본다. "통과할 것"·"이제 동작할 것"은 금지다. §11
3. **시그니처·API 응답·테이블을 바꾸면 소비자를 추적한다** — `kofia/`→`db/`→`web/routes/`→`frontend/src/`. 확인 없이 "영향 없음"이라고 말하지 않는다. §3
4. **UI 신규·수정은 전부 `frontend/src/` React** — API만 만들고 소비 컴포넌트를 안 만들면 사용자에게 안 보이는 orphan이다. admin은 `components/admin/` 아래 pane과 `pages/Admin.tsx` 탭, 새 페이지는 `pages/`와 `web/app.py` SPA 라우트다. §8
5. **DB 변경 전 `dev/DATA_MODEL.md` 먼저** — 불변 속성은 차원 한 곳에, 팩트는 denormalize하지 말고 JOIN한다. 설계 판단은 Fable 검토를 거친다. §9
6. **디버깅은 단일 가설·최소 변경, 3회 실패 시 STOP** — 증거와 함께 사용자에게 보고한다. §10
7. **구현·커밋은 자기 worktree에서만** — 공유 체크아웃은 main 고정 읽기 구역이다. 첫 편집 전에 브랜치와 경로를 확인하고, 아니면 멈춘다. §12

## 일관성 게이트 (anti-spaghetti)

> 산문 규칙은 세션이 길어지면 흘러내린다. 검사 가능한 규칙을 산문으로 단속하는 것 자체가 실패 메커니즘이다. 진단 전문은 `dev/LESSONS.md`.

1. **검사 가능한 규칙은 게이트로 강제** — 작성 시점 PostToolUse와 종료 시점 Stop 두 층이다. 게이트 목록·allowlist 정본은 `static_check.py` 헤더, 사람용 요약 지도는 `HARNESS.md`. 새 검사가능 규칙은 MD 문장 추가가 아니라 `static_check.py`에 검사를 더한다. 산문 드리프트는 월 1회 `/md-audit`이 상한선이다.
2. **게이트 우회 금지** — 소스 생성·수정은 반드시 Edit/Write로 한다. Bash 리다이렉트는 작성 시점 게이트를 우회한다. 400줄이나 나열 상한을 기계 분할로 때우는 것도 금지다. 분할과 개행은 의미 단위로 한다. `Any`/`any`로 때우지 않는다. 불가피하면 사유를 인라인 주석으로 남긴다. **게이트는 하한선이지 목표가 아니다.**
3. **래칫 원칙** — 대규모 정리는 그 상태를 잠그는 `static_check` 검사와 같은 커밋으로 끝낸다. baseline 파일은 감소만 허용한다.
4. **발명 금지, 모방 강제** — 새 코드 전에 `dev/CONVENTIONS.md`와 레이어 MD의 정본 예시를 Read해 그 형태를 모방한다. 임의로 형제 파일을 고르지 않는다. 갈리는 선택은 `dev/CONVENTIONS.md`에 등재한다. 일관성이 개인 취향보다 우선한다. 더 나은 패턴이 있으면 먼저 물어 정본을 바꾼 뒤 전파한다.

## 코딩·편집 원칙

**worktree 프로토콜** — 3단계 시작 시 `EDITING.md` 과업 보드를 확인하고 행을 등록한다. `#sid` 태그가 필수다. Stop 훅이 자기 행 잔존 시 종료를 막아 완료 보고를 강제한다. 이후 worktree로 격리하고, 구현과 검증을 전부 그 안에서 한 뒤, push·PR·CI·merge를 거쳐 보드 행을 제거한다. 서식과 충돌 해소 정본은 `EDITING.md`다.

**계획 단계 필수 항목** — 접근 방식, 변경될 실제 코드 스니펫, 정확한 경로, 브레이킹 체인지와 트레이드오프, 파일 설계표, 행동 검증 테스트다. 파일 설계표는 파일별 단일 책임 1줄과 예상 규모를 담고 400줄에 근접하면 미리 분할한다. 행동 검증 테스트는 수집·계산 로직마다 깨지면 실패하는 테스트 1개의 경로와 시나리오를 명시한다. 정본은 `dev/TESTING.md`다. **No Placeholders** — "TBD"·"나중에 구현"·"위와 유사하게"·정의되지 않은 참조가 있으면 plan 실패다.

**구현 단계** — plan Todo를 순서대로 실행하고 완료마다 체크한다. 모든 Todo가 끝날 때까지 멈추지 않는다.

**단순성 우선** — Lazy Ladder와 근본 원인 수정, 비타협 안전의 전문은 `.claude/hooks/lazy-persona.md`가 SessionStart에 주입한다. 요청 범위를 넘는 기능, 단일 사용 추상화, 불가능한 시나리오의 에러 핸들링은 만들지 않는다. `lazy:` 부채는 월 1회 `/lazy-debt`로 수확한다.

**외과적 변경** — 인접 코드·주석·포맷을 "개선"하지 않는다. 고장나지 않은 것은 리팩터하지 않는다. 내 스타일과 달라도 기존 스타일에 맞춘다. 관련 없는 dead code는 언급만 하고 삭제하지 않는다. 기준은 **변경된 모든 줄이 사용자 요청으로 직접 추적 가능한가**다.

## MD 시냅스 관리

**MD는 장기 기억이자 작동 규칙이다.** 변경한 영역의 정본 MD를 같은 턴에 갱신하되, 반드시 `dev/MD_STANDARD.md` 3원칙으로 쓴다. grep으로 알 수 있는 것은 적지 않는다. 어느 MD인지는 라우팅표의 역방향이다.

사용자의 지적과 피드백도 즉시 MD로 남긴다. 사고성이면 `dev/LESSONS.md`에 경위까지, UX 원칙이면 `design/UX.md`에 넣는다. "안정화 후 일괄"의 순간은 오지 않는다.

자명하지 않은 갱신처만 적는다. 새 React 페이지는 `frontend/FRONTEND.md`와 `web/app.py` SPA 라우트, 배치 스케줄은 `DEVGUIDE.md` 배치 표, DB 스키마는 `dev/DATA_MODEL.md`, 하네스 구성은 `HARNESS.md`다. 각각 게이트가 코드 실물과 대조한다.

**새 MD**를 만들면 같은 턴에 허브 라우팅표에 행을 추가한다. 없으면 읽힐 타이밍이 없고 게이트 ④D가 고아로 잡는다.

## 모델 라우팅 — 토큰 볼륨 × 판단 스테이크

메인 루프는 **Opus 5**다. 1M 컨텍스트라 정본 MD와 소스는 직접 Read가 기본이다. 위임은 비용 회피 수단이 아니라 **독립·병렬 대규모 작업의 병렬화 수단**이다.

| 역할 | 모델 | effort | 언제 |
|------|------|--------|------|
| 메인 루프 — 계획·구현·리서치·검수 | Opus 5 | high | 상시 |
| plan 최종 검토·아키텍처 중재 | Fable 5 단발 | high | plan 승인 요청 직전 1회 |
| DB 스키마 설계 판단 | Fable 5 단발 | high | 테이블·컬럼 신설이 담긴 plan |
| 디자인 미감 판단 | Fable 5 단발 | high | 새 디자인 언어·시안 채택 |
| 대규모 병렬 구현 지휘 | Fable 5 오케스트레이터 | high | 승인된 plan이 독립 트랙 3개 이상일 때 |
| 대량 기계적 정독·팬아웃 | Sonnet 5 에이전트 | medium | 수십 파일 독립 스캔 |

- **스폰 최소화** — 몇 번의 툴 호출로 끝날 일은 위임하지 않는다. 유일한 예외가 오케스트레이션이고, 발동 조건은 겹침을 공유로 뺀 뒤 서로소 트랙 3개 이상이다. 큰데 순차인 과업은 발동하지 않는다.
- **오케스트레이션 중에도 git·검증·보드는 메인 세션이 전담한다.** 워커 보고는 증거가 아니다.
- **비용 절감은 effort 하향이지 모델 다운그레이드가 아니다.** 장황함은 effort가 아니라 프롬프트로 제어한다.
- Fable 단발 호출의 입력은 결정에 필요한 요약과 파일 경로다. 원본을 대량으로 주입하지 않는다.
- **세션 분리** — 태스크가 머지로 완결되면 `/clear`한다. 프로젝트급 작업 여러 개를 한 세션에 끌고 가지 않는다.

## 하네스 등록

에이전트와 스킬은 세션에 자동 주입된다. 정본은 각 디렉토리 파일이고, **사람용 전체 지도는 `HARNESS.md`**다. 하네스 구성이 바뀌면 같은 턴에 지도를 갱신하고, 게이트 ④E가 실물과 대조한다. 모델과 effort는 각 에이전트 frontmatter가 정본이다.

> 훅 command는 상대경로로 등록한다. `%CLAUDE_PROJECT_DIR%` cmd 표기는 이 환경에서 확장되지 않아 훅이 통째로 실패한다. cwd는 프로젝트 루트가 보장된다.
