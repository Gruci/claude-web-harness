기능 추가·수정 4단계 워크플로우 — 리서치 → 계획 → 구현 → 수정/롤백.

> 담는 것: 각 단계에서 그대로 쓰는 프롬프트 문구. 담지 않는 것: 단계 규칙의 정본과 잠금·이견 병기 의무(→ `CLAUDE.md`). 읽는 시점: 새 기능·수정 요청을 받아 리서치부터 시작할 때.

AI가 독단적으로 코드를 작성하는 것을 방지하고, 설계를 문서(plan.md)로 남겨 사용자가 피드백을 주입한 뒤 구현을 시작한다.

## 트리거 조건
- 새 기능 추가 또는 기존 기능 수정 요청
- 버그 수정 (단순 오탈자·설정값 1줄 제외)
- 사용자가 "/feature-workflow" 또는 "리서치부터 해줘" 요청

---

## 📍 0단계: 범위 인터뷰 (리서치 착수 전)

요청에서 구현 시 정해져야 하는 갈림길(스코프 경계·노출 위치·적재 방식·어드민 취급 등)을 추려
AskUserQuestion 으로 **먼저 묻는다**. 답을 전제로 research 를 쓴다.
내가 임의로 권고안을 정해 plan ⚠️로 미루는 것보다 먼저 묻는 게 기본.

**브리프 패스트트랙** — 사용자가 아래 3요소를 요청에 이미 담았으면 인터뷰를 생략하고 바로 1단계로:

```
[브리프]
- 스코프: <포함/제외 경계 1줄>
- 노출: <어느 페이지/탭/드로어에 어떻게 1줄>
- 데이터: <소스→적재·저장 방식 1줄>
```

---

## 📍 1단계: 리서치 프롬프트

```
[목표: {작업할 기능 또는 분석할 문제}]

관련 파일들을 매우 깊이 읽고 현재 시스템이 어떻게 동작하는지 완벽하게 이해해라.
표면적으로 파일명이나 함수 시그니처만 훑지 말고,
내부 로직·데이터 흐름·다른 모듈과의 의존성까지 모든 세부 사항을 파악해라.

절대로 채팅창 안에서 구두로 요약해서 답변하지 마라.
리서치가 끝나면, 발견한 내용과 현재 시스템의 작동 방식을 매우 상세히 담은
`docs/tasks/research.md` 파일을 작성해라.

이 단계에서 소스 파일은 절대 수정하지 마라.
```

---

## 📍 2단계: 계획 프롬프트

```
방금 작성한 research.md를 바탕으로
[{구현할 기능}]을 위한 상세한 `docs/tasks/plan.md`를 작성해라.

포함 내용:
- 접근 방식 상세 설명
- 변경/추가될 실제 코드 스니펫 (실제 코드베이스 문맥 100% 반영 — 추상적 계획 금지)
- 수정될 파일의 정확한 경로
- 파일 설계표: 신규·수정 파일별 단일 책임 1줄 + 예상 규모 (400줄 근접이면 plan에서 미리 분할)
- 행동 검증 테스트: 신규·수정되는 수집·계산 로직마다 "이 로직이 깨지면 실패하는 테스트 1개"의
  파일 경로 + 검증 시나리오 (게이트 ⑫ — 없으면 구현 단계에서 막힌다)
- 트랙 후보: 병렬 가능한 작업 묶음과 각 묶음의 예상 편집 파일. 3개 미만이면 "미발동"과 사유 1줄
- 브레이킹 체인지·트레이드오프

명심:
1. 소스 파일을 꼼꼼히 읽고 실제 코드베이스의 문맥을 반영할 것.
2. No Placeholders — 모든 스텝에 실제 코드·실제 명령·정확한 경로. "TBD"·"나중에 구현"·
   "위와 유사하게"·정의되지 않은 타입/함수 참조 = plan 실패.
3. plan.md 작성이 끝나면 대기해라.
   내가 검토하고 승인하기 전까지 절대로 실제 코드 구현을 시작하지 마라.
```

> 이 목록의 정본은 `CLAUDE.md` 계획(2단계) — 항목이 갈리면 CLAUDE.md 를 따르고 여기를 동기화한다.

---

## 📍 2-1단계: 계획 검토·수정 반복 프롬프트

> plan.md를 에디터에서 열어 메모나 주석을 추가한 뒤 아래 프롬프트를 사용한다.

```
`docs/tasks/plan.md` 문서에 메모와 주석을 추가했어.
내가 추가한 모든 메모의 의도와 제약 조건을 완벽히 반영해서 plan.md를 다시 업데이트해라.
완료되면 알려주되, 아직 구현하지 마라.
```

> 만족할 때까지 반복. 확정되면: "좋아, 계획대로 진행할 Todo 리스트를 만들어줘"

---

## 📍 3단계: 구현 프롬프트

```
제시된 `docs/tasks/plan.md`와 Todo 리스트를 바탕으로 전부 구현해라.

- 작업이나 단계를 완료할 때마다 plan.md(또는 todo.md)에서 완료로 표시해라.
- 모든 작업이 완료될 때까지 멈추지 말고 계속 진행해라.
- EDITING.md 잠금 프로토콜 준수 (편집 전 등록 → 편집 → 해제).
```

**오케스트레이션 발동 시 (트랙 후보 3개 이상):**

1. 메인 세션이 보드 행 등록 → worktree 진입 → 베이스라인 커밋까지 먼저 끝낸다.
2. orchestrator 에이전트를 isolation 없이 1개 스폰하고 plan 경로와 트랙 후보를 넘긴다.
3. 오케스트레이터가 발동을 반려하면 메인 세션이 그대로 직접 구현한다.
4. 워커 전원이 끝나면 메인 세션이 이탈 검사와 pytest·static_check·빌드를 직접 돌린다.
5. Todo 체크·커밋·PR·머지는 메인 세션이 전담한다. 워커는 plan 파일을 편집하지 않는다.

이탈 검사는 변경 파일이 배정 합집합 안에 있는지 보는 것이다. 벗어난 파일은 워커가 배정을 넘은 것이라 머지 전에 판정한다.

```bash
git status --porcelain | awk '{print $2}' | sort
```

## 📍 4단계: 수정/롤백 프롬프트

**부분 수정 시:**
```
(스크린샷 또는 에러 로그 첨부)
이 부분에서 {원하는 결과}가 나와야 해.
다른 곳은 건드리지 말고 이 부분만 빠르고 정확하게 수정해.
```

**전면 롤백 시:**
```
방향이 잘못됐어. 방금 구현한 변경 사항들을 전부 이전으로 되돌려
(git restore/reset 또는 직접 롤백).
이제 {특정 좁은 기능}만 되도록 가장 심플하게 다시 작성해.
지정한 것 외엔 아무것도 변경하지 마.
```

## 완료 후 정리

구현이 완료되면 작업 파일을 archive로 이동한다:

```bash
mkdir -p docs/tasks/archive/YYYY-MM-DD-{작업명}
mv docs/tasks/research.md docs/tasks/archive/YYYY-MM-DD-{작업명}/
mv docs/tasks/plan.md     docs/tasks/archive/YYYY-MM-DD-{작업명}/
```
