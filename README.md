# claude-web-harness

**AI가 내 코드를 망치지 않게 잡아주는 가드레일**

하네스 v3.3.0

[한국어](README.md) · [English](README.en.md)

## 3줄 요약

1. Claude Code 같은 AI와 개발하다 보면 세션이 바뀔 때마다 AI가 약속을 잊고, 코드가 조금씩 어긋나기 시작합니다.
2. 이 도구는 그 약속을 문서가 아니라 **자동 검사**로 만들어서, 어기는 순간 저장 자체를 막습니다.
3. 설치 후 "하네스 깔아줘" 한마디면 설정이 끝나고, 이후에는 신경 쓰지 않아도 검사가 알아서 돕니다.

## 어떤 도구인가요?

초보 운전자가 실수해도 차가 알아서 멈추는 **자동 브레이크**를 떠올려 보세요. 이 도구는 AI가 규칙을 벗어난 코드를 쓰는 순간 저장을 멈추고 스스로 고치게 만드는, 개발용 가드레일입니다.

AI랑 대화하다 보면 코드가 꼬입니다. 어제 합의한 규칙을 오늘 세션은 모르고, "이 정도는 괜찮겠지"가 쌓이다 보면 어느새 아무도 못 읽는 코드가 됩니다. 규칙을 문서로 적어두는 것만으로는 막을 수 없습니다 — 문서는 부탁일 뿐, 강제가 아니니까요. 이 하네스는 규칙을 **차단**으로 구현합니다.

### 쓰기 전 / 쓴 후

| | 쓰기 전 | 쓴 후 |
|:--|:--|:--|
| 세션이 바뀌면 | 지난 합의를 잊고 제멋대로 작성합니다 | 세션과 무관하게 같은 규칙이 강제됩니다 |
| 규칙을 어기면 | 아무 일도 없습니다 — 나중에 사람이 발견합니다 | 저장 즉시 차단되고 AI가 수정합니다 |
| 코드 작성 순서 | 요청하자마자 바로 구현합니다 | 설계서를 승인하기 전에는 소스에 손대지 못합니다 |
| "다 됐어요" | 말뿐일 수 있습니다 | 전 검사를 통과해야 세션이 끝납니다 |
| 검사가 안 돌 때 | 조용히 통과한 것처럼 보입니다 | "안 돌았다"고 사유와 함께 보고됩니다 |

### 개발을 잘 몰라도 괜찮습니다 — 오히려 가장 필요한 분입니다

개발자는 AI가 이상한 코드를 쓰면 눈으로 알아챕니다. 개발을 모르면 "다 됐습니다"라는 말을 믿는 수밖에 없죠. 그런데 AI만 믿고 만든 프로젝트는 대개 이런 길을 갑니다.

1. 처음 며칠은 마법 같습니다. 말만 하면 기능이 생깁니다.
2. 코드가 쌓이면 AI가 자기가 만든 코드에 발이 걸리기 시작합니다. 기능 하나를 고치면 멀쩡하던 다른 곳이 깨집니다.
3. 어느 순간 "이 기능 추가해줘"가 더 이상 통하지 않고, 고치는 것보다 처음부터 다시 만드는 게 빠른 지경이 됩니다. 그동안 쓴 시간과 비용은 돌아오지 않습니다.

이 도구는 그 2번 단계가 오지 않게 막습니다. 코드를 읽을 줄 아는 사람이 옆에서 매번 검사해주는 것과 같은 효과를, 자동 검사가 대신합니다. AI의 "다 됐습니다"는 검사를 통과했을 때만 인정되고, 통과 못 하면 AI가 스스로 고칠 때까지 세션이 끝나지 않습니다. **코드를 볼 줄 몰라도, 코드가 무너지지 않습니다.**

### 이럴 때 쓰세요

- **개발을 모르지만** AI로 서비스를 만들고 있고, 어느 날 갑자기 멈출까 불안할 때
- Claude Code로 **프로젝트를 처음부터** 만들려는데, 코드가 산으로 갈까 걱정될 때
- AI와 오래 협업하며 **일관성이 무너지는 것**을 이미 겪어본 개발자
- "설계 먼저, 구현은 승인 후" 흐름을 **말이 아니라 시스템으로** 강제하고 싶을 때

화면 있는 웹 서비스, API 서버, 배치 작업 어디든 붙습니다. Python 외 언어(Go·TypeScript)도 설정 한 줄로 지원합니다.


## harness_profile.py — 유일하게 손댈 설정 파일

온보딩이 자동으로 만들어주므로 처음에는 열어볼 필요가 없습니다. 나중에 프로젝트 구조가 바뀌었을 때 이 파일 하나만 고치면 됩니다.

왜 필요할까요? 검사 로직 자체는 프로젝트를 모릅니다. "조회 전용 폴더에서는 데이터를 고치면 안 된다"는 **규칙의 형태**만 알고, 그 폴더가 어디인지는 이 파일이 알려줍니다. 그래서 프로젝트마다 검사기를 고칠 필요 없이 이 파일만 갈아끼우면 됩니다.

```python
# harness_profile.py — 검사 대상 언어 (한 줄로 확장자·관용구·도구가 따라옵니다)
LANG = "go"                       # kernel/langs/go.py

# 프로젝트 형태 (한 줄로 성립하지 않는 검사가 [N/A]로 정리됩니다)
# 화면이 없는 서비스라면 화면 검사는 "설정 누락"이 아니라 "해당 없음"입니다.
ARCH = "backend_only"             # web_layered / backend_only / headless

# 레이어 경로 정의
# 키는 검사기가 아는 역할, 값은 이 프로젝트의 실제 경로입니다.
# 값이 None이면 그 역할을 쓰는 검사는 [SKIP] 상태가 됩니다.

LAYERS: dict[str, str | None] = {
    "read":      "db/reads",      # 조회 전용. 쓰기 SQL 금지 검사가 여기를 봅니다
    "write":     "db/writes",     # 변경 전용
    "db":        "db",            # 커넥션 점유 검사 대상
    "web":       "api",           # 기본값 "web"에서 바꾼 예시입니다
    "routes":    "api/routes",    # 상위 경로를 바꾸면 함께 고칩니다
    "ui":        "frontend/src",  # None으로 두면 화면 관련 검사 7종이 쉽니다
    "tests":     "tests",
    "schema":    "db/schema",
    "shared":    "utils",
    "batch":     "batches",
}
```

폴더 이름이 실제와 다르면 바꾸면 됩니다. 설정과 실제 구조가 어긋나면 배치 검사가 잡아주므로, 이름을 바꾸고 잊은 채 검사가 조용히 헛도는 일은 없습니다.

주요 설정 항목입니다.

| 항목 | 용도 |
|:--|:--|
| `STAGE` | 프로젝트 성숙도. `greenfield` / `growing` / `mature` |
| `LANG` | 서버 언어. 확장자·관용구·외부 도구가 함께 결정됩니다 |
| `ARCH` | 프로젝트 형태. 화면·웹 서버가 없는 구성에서 성립하지 않는 검사를 `[N/A]`로 보고합니다 |
| `LAYERS` | 역할별 실제 경로. 안 적으면 해당 검사가 쉽니다 |
| `FILES` · `SYMBOLS` | 설정 모듈, 커넥션 헬퍼 같은 프레임워크별 이름 |
| `SCOPE` | 검사에서 뺄 경로. 벤더 사본, 산출물, 픽스처 |
| `VOCAB` | 금지 축약어와 화면에 노출하면 안 되는 내부 용어 |
| `ALLOWLIST` | 파일 단위 영구 면제 목록 |
| `DOC_SYNC` | 문서와 코드에 중복 기재된 값의 대조 쌍 |
| `AGENT_MODEL_POLICY` | 역할별 AI 모델 고정값 |
| `MAINTENANCE` | 정기 점검이 뜨는 임계치 |
| `LOCAL_GATES` | 이 저장소 전용 검사 목록 |

## 일상 개발은 이렇게 흘러갑니다

기능을 요청하면 다음 5단계를 거칩니다. 당신이 개입하는 지점은 **질문에 답하기**와 **설계서 승인** 두 곳뿐입니다.

```
[1. 질문·분석] → [2. 설계서 작성] → [3. 승인 대기] → [4. 구현·검사] → [5. 정리·재검증]
                                          ▲
                                     당신이 개입하는 지점
```

| 단계 | 일어나는 일 | 소스 변경 |
|:--:|:--|:--:|
| 1 | 적용 화면, 사용 데이터, 작업 범위를 물어봅니다. 관련 코드를 직접 열어 데이터 흐름을 분석합니다 | 없음 |
| 2 | 설계서를 파일로 만듭니다. 정확한 파일 경로, 실제 코드 조각, 예상 파급 범위가 들어갑니다 | 없음 |
| 3 | 당신의 검토와 승인을 기다립니다 | 없음 |
| 4 | 승인된 설계서대로 구현합니다. 저장할 때마다 검사가 돕니다 | 발생 |
| 5 | 관련 문서를 갱신하고 작업 파일을 정리합니다. 종료 시 전체 검사를 다시 돕니다 | 발생 |

설계서에 `TBD`, "나중에 구현", "위와 유사하게" 같은 미확정 표현이 있으면 설계서로 인정되지 않고 반려됩니다. 화면 시안이 필요한 작업은 `docs/tasks/mockup/`에 시안 파일을 먼저 만들어 승인받고, 승인된 시안 그대로 구현합니다. 작업이 끝나면 조사·설계·시안 파일이 함께 `docs/tasks/archive/`로 정리됩니다.

## 자주 묻는 질문

**파이썬이 아닌 언어에서도 쓸 수 있나요?**
네. 설정에 `LANG = "go"` 한 줄만 적으면 확장자, 관용구, 그 언어에서 성립하지 않는 규칙 목록, 위임할 외부 도구가 함께 적용됩니다. `python`·`go`·`typescript`가 기본 제공되고, 그 외 언어는 `profiles/lang/<이름>.py`에 네 항목(`EXT`·`PATTERNS`·`NOT_APPLICABLE`·`LINTERS`)만 선언하면 됩니다. 구문 분석이 필요한 검사는 그 언어의 표준 도구(Go는 `go vet`·`staticcheck`, Python은 `ruff`, TypeScript는 `tsc`·`eslint`)에 맡깁니다. 도구가 없으면 통과가 아니라 `[TOOL]`로 표시되고 설치 명령을 알려줍니다.

**기술 스택을 못 정했는데 설치해도 되나요?**
네. 온보딩은 기술명이 아니라 만들려는 것의 형태를 물어봅니다. "미정"을 고르면 가장 보편적인 구성으로 설치되고, 안 쓰는 영역의 검사는 쉬는 상태로 유지됩니다.

**화면이 없는 서비스인데 화면 검사가 "설정 미비"로 계속 표시됩니다.**
`ARCH = "backend_only"`(서버만 있음) 또는 `ARCH = "headless"`(웹·화면 모두 없음)를 선언해 보세요. 해당 검사들이 `[SKIP]`(설정을 안 채움)이 아니라 `[N/A]`(이 프로젝트 형태에는 채울 것이 없음)로 보고됩니다. 잃은 것과 원래 없는 것이 출력에서 구분됩니다.

**설치 후에 프로젝트 성격이 바뀌면요?**
`harness_profile.py`의 해당 항목만 고치면 됩니다. 화면 없이 시작했다가 화면을 추가하는 경우 `ARCH`를 `web_layered`로 바꾸고 `LAYERS["ui"]` 한 항목을 적으면 화면 관련 검사 7종이 대상을 모으기 시작합니다.

**특정 검사가 우리 프로젝트에 안 맞으면 끌 수 있나요?**
해당 설정 항목을 비우면 `[SKIP]` 상태가 됩니다. 다만 쉰다는 사실은 매 실행마다 사유와 함께 출력되고, 이를 숨기는 설정은 일부러 만들지 않았습니다.

**개발자가 직접 써야 하는 건 뭔가요?**
설치 시점에는 없습니다. 폴더명과 프레임워크 함수명은 온보딩이 처리합니다. 개발자만 아는 것은 그 서비스의 도메인 지식이고, `PROJECT.md`에 개발하면서 조금씩 쌓으면 됩니다.

**GitHub 저장소를 미리 만들어야 하나요?**
`gh` 인증이 돼 있다면 비공개 저장소를 자동으로 만들어 푸시합니다. 공개 저장소는 되돌리기 어려우므로 명시적으로 요청할 때만 만듭니다. 인증이 없을 때만 저장소 주소를 물어봅니다.

**모바일 앱으로 확장할 계획이 있다면요?**

<details>
<summary>화면을 포함하는 프로젝트의 앱 이식 대비 규칙</summary>

현재 개발 기준은 웹입니다. 다만 앱으로 옮길 때 재사용할 것과 버릴 것이 미리 구분되도록, 재사용 대상을 초기부터 분리해 둡니다.

| 규칙 | 이식할 때 |
|:--|:--|
| 계산·데이터 가공을 화면 파일 밖에 두기 | 로직 그대로 이동 |
| 색상·간격·글자 크기를 정본 파일에서만 참조 | 값 그대로 재사용 |
| 브라우저 전용 기능은 단일 래퍼 경유 | 그 파일만 교체 |
| 페이지 이동 코드를 페이지 계층에 한정 | 교체 범위 최소화 |

앱을 만들게 되면 화면 계층만 다시 구현하고 서버·로직·디자인 값은 그대로 가져갑니다. 앱을 안 만들어도 손해는 없습니다 — 이 분리는 그 자체로 좋은 구조니까요.

</details>

### 설계 원칙

| 원칙 | 구현 방식 |
|:--|:--|
| **설계 우선** | 코드 작성 전 설계서를 파일로 만들고 승인을 받습니다. 승인 전에는 소스가 변경되지 않습니다 |
| **저장 시점 검증** | 파일 저장 직후 정적 검사가 돌고, 위반 시 그 변경을 차단하고 수정을 요구합니다 |
| **종료 시점 재검증** | 대화 종료 시 전체 검사를 다시 돕니다. 미해결 위반이 있으면 세션이 끝나지 않습니다 |
| **스택 비종속** | 판정 로직은 프로젝트를 모릅니다. 프로젝트별 값은 설정 파일 한 곳에 격리됩니다 |
| **미검증은 미검증으로 보고** | 언어·설정 때문에 못 돈 검사는 통과가 아니라 `[SKIP]`으로, 사유와 함께 출력됩니다 |

### 검사 결과 여섯 등급

수행하지 못한 사유를 셋으로 나눈 것이 이 도구의 핵심입니다 — 각각 해야 할 일이 다르기 때문입니다.

| 등급 | 의미 | 할 일 | 세션 종료 |
|:--|:--|:--|:--:|
| `[OK]` | 수행했고 위반 없음 | — | 허용 |
| `[SKIP]` | 설정이 없어 안 돌았음 | 설정을 채우면 활성화 | 허용 |
| `[N/A]` | 이 언어·프로젝트 형태에서 규칙이 성립하지 않음 | **없음 — 손실이 아닙니다** | 허용 |
| `[TOOL]` | 외부 도구가 없어 못 돌았음 | 도구 설치 시 활성화 | 허용 |
| `[FAIL]` | 위반 검출 | 수정 | 차단 |
| `[REPORT]` | 오탐 가능성이 있는 연성 신호 | 판단 | 허용 |

> **`[SKIP]`은 통과가 아닙니다.** 이전 세대 도구는 이 상태를 통과로 처리했고, 그 결과 폴더명 하나가 어긋났을 뿐인데 8종의 검사가 조용히 멈춘 채 정상 신호를 냈습니다.

### 막을지 말할지는 근거가 정합니다

같은 위반이라도 **어떻게 알아냈는지**에 따라 처리가 다릅니다.

| 근거 | 처리 | 예 |
|:--|:--|:--|
| **직접 봤음** — 검사기가 위반을 뱉었거나 파일이 실제로 거기 있음 | 차단 | 규칙 위반, 정리 안 된 산출물 |
| **추측했음** — git 상태로 "끝났을 것"을 미루어 판단 | 경고만 (막지 않음) | 작업 사본·작업 목록 정리 알림 |

추측으로 막으면 틀렸을 때 빠져나갈 길이 없습니다. 실제로 그런 일이 있었습니다 — 방금 만든 작업 사본을 "다 끝났으니 지우라"고 요구하거나, 아직 병합 전인 작업 기록을 지우라며 세션을 끝내지 못하게 붙잡았습니다. 지금은 **검출은 계속하되 문은 잠그지 않습니다.**

### 어떤 것들을 잡아주나요

파일을 저장할 때마다 35종의 검사가 돕니다. 전체 목록과 판정 근거는 `HARNESS.md`에 있습니다. 대표 예시입니다.

| 잡히는 것 | 왜, 어떻게 고치나 |
|:--|:--|
| 조회 전용 레이어에서 데이터 변경·삭제 SQL | 레이어 책임 위반. 변경 작업은 쓰기 레이어로 |
| 화면 코드에 색상값 하드코딩 (`#ff8800`) | 색상 정본 파일이나 CSS 변수를 거치도록 |
| 고정 픽셀 너비 (`width: 420px`) | 모바일이 깨집니다. `max-width`·`%`·`clamp`로 |
| 한 파일 400줄 초과 | 단일 책임 상실. 기능 단위로 분할 |
| 소스에 API 키 하드코딩 | 설정 모듈 경유. 이미 커밋됐다면 키 회전까지 |
| 문서에 적힌 파일 경로가 실존하지 않음 | 삭제·이름변경 후 남은 참조 정리 |
| 공개 함수의 타입힌트 누락 | 모듈 경계면 명세화 |
| AI 에이전트 정의와 모델 정책표 불일치 | 모델 배정이 정책과 어긋나지 않게 |
| API는 만들었는데 그 화면이 없음 | 사용자에겐 없는 기능입니다. 화면까지가 한 단위 |
| 이름만 바꿔 다시 만든 함수 | 이미 있는 정본을 쓰거나, 공용으로 뽑아 한 벌만 |
| 상수 이름을 바꾸고 한 곳을 놓침 | 실행은 되고 그 화면을 눌러야 터집니다. 저장 시점에 잡습니다 |

검사가 도는 시점은 세 곳입니다.

| 시점 | 대상 | 위반 시 |
|:--|:--|:--|
| 파일 저장 직후 | 그 파일 | 변경 차단, 수정 요구 |
| 세션 종료 시도 | 전체 | 세션 종료 차단 |
| 수동 실행 (`python -X utf8 -m kernel.runner`) | 전체 | 종료 코드 1 |

### 프로젝트 구조

```
project-root/
├── harness_profile.py      # 프로젝트별 설정 정본 (폴더명·용어·예외)
├── harness_install.py      # 설치와 기존 위반 등록 스크립트
├── CLAUDE.md               # AI 행동 규칙. 세션마다 자동 로드
├── PROJECT.md              # 서비스 도메인 정의, 용어, 레이어 구조
├── HARNESS.md              # 검사·훅·에이전트·스킬 전체 지도
├── DEVGUIDE.md             # 서버 개발 규칙 (dev/ 연계)
├── DESIGN_GUIDE.md         # 화면 디자인 규칙 (design/ 연계)
├── EDITING.md              # 동시 세션 충돌 방지용 작업 현황판
├── kernel/                 # 검사 판정 엔진. 프로젝트를 모릅니다
│   ├── langs/              # 언어팩 — 언어별 선언
│   └── archs/              # 아키텍처팩 — 프로젝트 형태별 선언
├── profiles/               # 프로젝트 유형별 설정 프리셋
├── harness_gates/          # 이 저장소 전용 검사 (선택)
├── tests/                  # 검사기 자체의 회귀 방지 장치
└── .claude/                # 훅, 에이전트, 스킬, 세션 설정
```

계층은 단순합니다. 훅(자동 실행)이 검사 엔진(`kernel/`)을 부르고, 엔진은 규칙의 **형태**만 알며, 그 규칙이 적용될 실제 폴더·이름은 `harness_profile.py`가 알려줍니다. 예를 들어 "조회 전용 레이어에서 쓰기 SQL 금지"라는 판정은 `kernel/`에 있고, 그 레이어의 실제 경로는 설정 파일이 정합니다.

### 수동 설치

세션을 거치지 않고 직접 설치하려면:

```bash
python -X utf8 harness_install.py --list                      # 프리셋 목록 확인
python -X utf8 harness_install.py --preset web_fastapi_react  # 설정 파일 생성
# harness_profile.py 의 폴더명을 실제 구조에 맞게 고친 후
python -X utf8 harness_install.py                             # 기존 위반 등록과 검증
python -X utf8 setup_global_permissions.py                    # 전역 권한 병합
```

사전 요구사항은 Git 저장소(필수 — 검사 대상을 `git ls-files`로 모으므로 미초기화 시 전 검사가 헛돕니다), GitHub 원격(필수 — 미설정 시 세션 종료가 막힙니다), Python(필수), Node.js(선택 — UI 품질 점검 시)입니다.

### 기존 프로젝트에 도입하기

레거시 코드가 있으면 첫 검사에서 위반이 쏟아질 수 있습니다. 그대로 두면 검사를 꺼버리게 되므로, 설치 스크립트가 **도입 시점의 기존 위반을 미리 등록해 예외 처리**합니다.

| 대상 | 처리 |
|:--|:--|
| 도입 시점에 이미 있던 위반 | `(검사 항목, 파일)` 단위로 등록, 검사에서 제외 |
| 등록된 파일을 나중에 수정할 때 | 위반을 고치고 등록을 삭제 |
| 새로 만드는 파일 | 예외 없이 전 검사 통과 |

등록 목록은 줄어들기만 합니다. 정리는 이렇게 합니다.

```bash
python -X utf8 harness_install.py --dry-run   # 등록 예정 항목 확인
python -X utf8 harness_install.py --prune     # 수정 완료 항목 정리
```

### 검사 규칙을 늘리는 방법

장애나 작업 실수가 생기면 이 절차로 규칙이 늘어납니다.

| 단계 | 하는 일 | 남는 것 |
|:--:|:--|:--|
| 1 | 사고 경위와 손실을 기록합니다. 대가를 함께 적어야 다음 세션이 예외로 넘기지 않습니다 | `dev/LESSONS.md` |
| 2 | 기계로 검출할 수 있는지 판단합니다 | — |
| 3 | 가능하면 검사로 구현합니다. 범용 규칙은 `kernel/`, 이 저장소 전용은 `harness_gates/` | 검사 모듈 |
| 4 | 불가능하면 "산문 전용"과 사유를 명시합니다 | `dev/LESSONS.md` |

3도 4도 안 하면 그 자체를 검사가 잡습니다. 판단을 미룬 상태이기 때문입니다.

### 정기 점검 — 도구가 때를 알려줍니다

프로젝트가 커지면 문서·코드 불일치, 과설계, 미처리 부채가 쌓입니다. 이 도구는 저장소 실물에서 임계치를 재서 점검 시점을 스스로 판단하고, 세션 시작 때 알려줍니다. 진행 중인 작업이 끝나면 자동으로 돌고, 모든 점검은 보고서만 만들 뿐 소스를 건드리지 않습니다. 임계치는 `harness_profile.py`의 `MAINTENANCE`에서 조정합니다.

### Claude를 여러 개 띄워서 개발하고 싶다면

프로젝트가 커지면 욕심이 생깁니다. 화면은 이 세션에, API는 저 세션에 맡기고 동시에 달리게 하고 싶죠. 그런데 그냥 띄우면 언젠가 사고가 납니다 — 하나의 작업 폴더를 여럿이 쓰다가 서로의 작업을 덮어쓰고, 어느 날 남의 커밋에 내 코드가 쓸려 들어갑니다.

이 도구에는 그 사고를 실제로 겪고 다듬어진 협업 규약이 들어 있습니다. 세션마다 격리된 작업 사본을 받아 각자 거기서 작업하고, git 머지로 합칩니다. 그리고 늘 그렇듯 — 규약은 부탁이 아니라 **차단**으로 지켜집니다.

- 작업 사본 이름에 세션 표식이 자동으로 박힙니다. 목록 한 번이면 "지금 누가 뭘 하는지"가 보입니다.
- 작업 사본이 하나라도 생기는 순간, 공유 폴더는 자동으로 읽기 전용 구역이 됩니다. 병렬이 시작됐다는 뜻이니까요.
- 검사를 피해 셸로 몰래 소스를 고치는 것, 검사 결과가 나오기 전에 머지해버리는 것 — 실행되기 전에 막힙니다.
- 끝난 작업 사본을 안 치우면 세션이 안 끝납니다. "나중에 정리"는 오지 않는다는 걸 도구가 압니다.
- 설계가 서로 겹치지 않는 3갈래 이상으로 나뉘면, 지휘 전담 AI가 파일 소유권을 나눠 여러 AI를 동시에 굴립니다.

혼자 한 세션으로 쓸 때는요? 이 전부가 조용히 잠들어 있습니다. 병렬을 시작하는 순간에만 깨어납니다.

### AI 모델 역할 분담

작업 성격에 따라 모델 등급을 나눠 씁니다. 이 배정도 검사 대상이라, 정책표와 실제 배정이 어긋나면 세션이 끝나지 않습니다.

| 모델 | 담당 | 기준 |
|:--|:--|:--|
