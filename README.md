## 1. 개요

AI와의 대화 세션이 종료되면 이전에 합의한 규약과 코딩 스타일은 유실됩니다. 다음 세션은 그 맥락을 알지 못한 채 자체 판단으로 코드를 생성하며, 이러한 편차가 누적되면 코드베이스의 일관성이 붕괴됩니다.

규칙을 문서로만 기록하는 방식은 강제력이 없습니다. 산문 형태의 규약은 사람과 AI 모두에게 우회가 용이하기 때문입니다. 본 하네스는 규칙을 요청이 아닌 **차단**으로 구현합니다.

### 1.1 설계 원칙

| 원칙 | 구현 방식 |
|:--|:--|
| **설계 우선** | 코드 작성 전 설계서를 파일로 생성하고 승인을 받습니다. 승인 이전에는 소스가 변경되지 않습니다 |
| **저장 시점 검증** | 파일 저장 직후 정적 검사가 실행되며, 위반 시 해당 변경을 차단하고 수정을 요구합니다 |
| **종료 시점 재검증** | 대화 종료 시 전체 검사를 재실행합니다. 미해결 위반이 존재하면 세션이 종료되지 않습니다 |
| **스택 비종속** | 판정 로직은 프로젝트를 인지하지 않습니다. 프로젝트별 값은 설정 파일 한 곳에 격리됩니다 |

### 1.2 검사 상태 정의

검사 결과는 네 등급으로 보고됩니다. `[OK]`와 `[SKIP]`의 구분이 본 도구의 핵심 설계 요소입니다.

| 등급 | 의미 | 세션 종료 |
|:--|:--|:--:|
| `[OK]` | 검사를 수행했으며 위반 없음 | 허용 |
| `[SKIP]` | **검사에 필요한 설정이 없어 수행되지 않음** | 허용 |
| `[FAIL]` | 위반 검출 | 차단 |
| `[REPORT]` | 오탐 가능성이 있는 연성 신호. 총계에 미합산 | 허용 |

> **`[SKIP]`은 통과가 아닙니다.** 설정 누락으로 검사가 비활성 상태임을 의미합니다. 이전 세대 도구는 이 상태를 통과로 처리했으며, 그 결과 폴더명 하나가 설정과 불일치할 경우 8종의 검사가 무동작 상태로 정상 신호를 반환했습니다.

## 2. 시작하기

### 2.1 설치

```bash
# 1. 저장소 복제 및 이동
git clone https://github.com/WooriGrunda/claude-web-harness.git my-project
cd my-project

# 2. Git 이력 초기화 및 최초 커밋
rm -rf .git && git init && git add -A && git commit -m "init"

# 3. Claude Code 실행
claude
```

실행 후 세션에서 다음과 같이 지시합니다.

```
하네스 깔아줘
```

온보딩 절차가 프로젝트 유형 확인, 설정 파일 생성, 원격 저장소 연결, 비활성 검사 점검까지 수행합니다.

### 2.2 프로젝트 유형 선택

설치 과정에서 다음 4개 유형 중 하나를 선택합니다. 선택 결과에 따라 해당 유형에 필요한 검사만 활성화됩니다.

| 유형 | 대상 | 적용 프리셋 |
|:--|:--|:--|
| 화면 기반 서비스 | 로그인·대시보드 등 브라우저에서 사용하는 애플리케이션 | `web_fastapi_react` |
| API 전용 서비스 | 화면 없이 데이터만 송수신하는 백엔드 | `api_fastapi` |
| 배치·자동화 작업 | 수집, 집계, 리포트 생성 등 주기 실행 작업 | `batch_python` |
| 미정 | 결정 이전 단계. 가장 보편적인 구성으로 설치하며 미사용 검사는 자동 비활성화 | `web_fastapi_react` |

기술 스택명을 사전에 파악할 필요는 없습니다. 온보딩은 결과물의 형태를 질의하며, 스택 선정과 근거 제시는 도구가 수행합니다.

### 2.3 수동 설치

세션을 경유하지 않고 직접 설치하는 경우 다음 절차를 따릅니다.

```bash
python -X utf8 harness_install.py --list                      # 프리셋 목록 및 용도 확인
python -X utf8 harness_install.py --preset web_fastapi_react  # 설정 파일 생성
# harness_profile.py 의 폴더명을 실제 구조에 맞춰 수정한 후
python -X utf8 harness_install.py                             # 기존 위반 등록 및 검증
python -X utf8 setup_global_permissions.py                    # 전역 권한 병합
```

### 2.4 사전 요구사항

| 항목 | 필수 여부 | 사유 |
|:--|:--:|:--|
| Git 저장소 | 필수 | 검사 대상 목록을 `git ls-files` 기준으로 수집합니다. 미초기화 시 검사 대상이 0건이 되어 전 검사가 무력화됩니다 |
| GitHub 원격 | 필수 | 미설정 시 세션 종료가 차단됩니다. `gh` 인증이 있으면 비공개 저장소를 자동 생성합니다 |
| Python | 필수 | 검사기 실행 환경 |
| Node.js | 선택 | UI 품질 점검 도구 사용 시에만 필요 |

## 3. 일일 개발 워크플로우

기능 추가 및 변경 요청은 다음 5단계를 거칩니다. 개발자가 개입하는 지점은 **질의 응답**과 **설계 승인** 두 곳입니다.

```
[1. 질의·분석] → [2. 설계서 작성] → [3. 승인 대기] → [4. 구현·검사] → [5. 정리·재검증]
                                          ▲
                                    개발자 개입 지점
```

| 단계 | 수행 내용 | 소스 변경 |
|:--:|:--|:--:|
| 1 | 적용 화면, 사용 데이터, 작업 범위를 질의합니다. 관련 코드를 직접 열람하여 데이터 흐름과 모듈 의존성을 분석합니다 | 없음 |
| 2 | 설계서를 파일로 생성합니다. 정확한 파일 경로, 실제 코드 스니펫, 예상 파급 범위를 포함합니다 | 없음 |
| 3 | 개발자의 검토 및 승인을 대기합니다 | 없음 |
| 4 | 승인된 설계서에 따라 구현합니다. 저장 시점마다 검사가 실행됩니다 | 발생 |
| 5 | 관련 문서를 갱신하고 작업 파일을 정리합니다. 종료 시 전체 검사를 재실행합니다 | 발생 |

### 3.1 설계서 요건

다음 항목이 누락된 산출물은 설계서로 인정되지 않으며 2단계가 반려됩니다.

- 정확한 파일 경로 및 파일별 단일 책임 기술
- 실제 코드 스니펫 (의사 코드 불가)
- 브레이킹 체인지 및 트레이드오프 명시
- 화면 작업의 경우 데스크톱·모바일 배치를 모두 포함한 반응형 설계표
- `TBD`, `나중에 구현`, `위와 유사하게` 등 미확정 표현 부재

## 4. 자동 검사 규칙

파일 저장 시점에 30종의 검사가 실행됩니다. 위반 검출 시 해당 변경은 차단되며 수정 요구가 반환됩니다. 전체 목록과 판정 근거는 `HARNESS.md`에 정의되어 있습니다.

### 4.1 주요 규칙 예시

| 위반 사례 | 차단 사유 및 개선 방향 |
|:--|:--|
| 조회 전용 레이어에서 데이터 변경·삭제 SQL 실행 | 레이어 책임 분리 위반. 변경 작업은 쓰기 레이어로 이관 |
| 화면 코드 내 색상값 하드코딩 (`#ff8800`) | 색상 정본 파일 또는 CSS 변수 경유로 제한 |
| 고정 픽셀 너비 지정 (`width: 420px`) | 모바일 뷰포트 대응. `max-width`·`%`·`clamp` 등으로 대체 |
| 단일 파일 400줄 초과 | 단일 책임 상실. 기능 단위 분할 필요 |
| 소스 내 API 키 등 인증 정보 하드코딩 | 설정 모듈 경유. 이미 커밋된 경우 키 회전까지 요구 |
| 문서에 기재된 파일 경로가 실존하지 않음 | 문서·코드 동기화. 삭제·리네임 후 잔존 참조 제거 |
| 공개 함수의 타입힌트 누락 | 모듈 경계면 명세화 |
| 에이전트 정의와 모델 정책표 불일치 | 모델 배정이 정책과 어긋나는 상태 방지 |

### 4.2 비활성 검사 확인

설정 누락으로 수행되지 않은 검사는 사유와 함께 출력됩니다.

```
[SKIP] 브라우저 API 직접 호출 — 설정에 브라우저 API 래퍼를 안 적었음
[SKIP] DDL 저장 타입 잘림 — 설정에 schema 폴더를 안 적었음
```

해당 항목이 프로젝트에 필요한 검사라면 `harness_profile.py`의 대응 항목을 기입하여 활성화합니다. 프로젝트 특성상 불필요한 경우(예: 화면이 없는 서비스의 UI 검사) 비활성 상태를 유지하되, 비활성 사실은 매 실행 시 보고됩니다.

### 4.3 검사 실행 시점

| 시점 | 대상 | 위반 시 |
|:--|:--|:--|
| 파일 저장 직후 | 해당 파일 | 변경 차단 및 수정 요구 |
| 세션 종료 시도 | 전체 | 세션 종료 차단 |
| 수동 실행 (`python -X utf8 -m kernel.runner`) | 전체 | 종료 코드 1 반환 |

## 5. 프로젝트 구조 및 설정

### 5.1 디렉토리 구성

```
project-root/
├── harness_profile.py      # 프로젝트별 설정 정본 (폴더명·용어·예외 정의)
├── harness_install.py      # 설치 및 기존 위반 등록 스크립트
├── CLAUDE.md               # AI 행동 규칙. 스택 비종속 골격, 세션마다 자동 로드
├── PROJECT.md              # 서비스 도메인 정의, 용어, 레이어 구조 명세
├── HARNESS.md              # 검사·훅·에이전트·스킬 전체 지도
├── DEVGUIDE.md             # 서버 개발 규칙 (dev/ 연계)
├── DESIGN_GUIDE.md         # 화면 디자인 규칙 (design/ 연계)
├── EDITING.md              # 동시 세션 충돌 방지용 작업 현황판
├── kernel/                 # 검사 판정 엔진. 프로젝트를 인지하지 않음
├── profiles/               # 프로젝트 유형별 설정 프리셋
├── harness_gates/          # 해당 저장소 전용 검사 (선택)
├── tests/                  # 검사기 자체의 회귀 방지 픽스처 및 정답지
└── .claude/                # 훅 14종, 에이전트 6종, 스킬 10종, 세션 설정
```

### 5.2 계층 구조

```
사용자
 └─ Claude Code 세션
     ├─ 스킬 (작업 절차)
     ├─ 에이전트 (분야 전담)
     └─ 훅 (자동 실행)
         └─ kernel/ (판정 로직 — 프로젝트 비인지)
             └─ harness_profile.py (프로젝트 고유 값)
```

하위 계층이 상위 계층을 강제합니다. 판정 로직은 규칙의 **형태**만 보유하며, 그 규칙이 적용될 대상은 설정 파일이 지정합니다. 예를 들어 "조회 전용 레이어에서 쓰기 SQL 금지"라는 판정은 `kernel/`에 있고, 해당 레이어의 실제 경로는 `harness_profile.py`가 정의합니다.

### 5.3 설정 커스터마이징

프로젝트 이식 시 수정 대상은 원칙적으로 `harness_profile.py` 단일 파일입니다.

```python
# harness_profile.py — 레이어 경로 정의
# 키는 검사기가 인지하는 역할, 값은 해당 프로젝트의 실제 경로입니다.
# 값이 None이면 그 역할을 사용하는 검사는 [SKIP] 상태가 됩니다.

LAYERS: dict[str, str | None] = {
    "read":      "db/reads",      # 조회 전용. 쓰기 SQL 금지 검사 대상
    "write":     "db/writes",     # 변경 전용
    "db":        "db",            # 커넥션 점유 검사 대상
    "web":       "api",           # 기본값 "web"에서 변경한 사례
    "routes":    "api/routes",    # 상위 경로 변경에 맞춰 함께 수정
    "ui":        "frontend/src",  # None으로 두면 화면 관련 검사 7종 비활성화
    "tests":     "tests",
    "schema":    "db/schema",
    "shared":    "utils",
    "batch":     "batches",
}
```

주요 설정 항목은 다음과 같습니다.

| 항목 | 용도 |
|:--|:--|
| `STAGE` | 프로젝트 성숙도. `greenfield` / `growing` / `mature` |
| `LAYERS` | 역할별 실제 경로. 미선언 시 해당 검사 비활성화 |
| `FILES` · `SYMBOLS` | 설정 모듈, 커넥션 헬퍼 등 프레임워크별 이름 |
| `SCOPE` | 검사 제외 경로. 벤더 사본, 산출물, 픽스처 |
| `VOCAB` | 금지 축약어 및 화면 노출 금칙어 |
| `ALLOWLIST` | 파일 단위 영구 면제 목록 |
| `DOC_SYNC` | 문서와 코드에 중복 기재된 값의 대조 쌍 |
| `AGENT_MODEL_POLICY` | 역할별 모델·effort 고정값 |
| `MAINTENANCE` | 정기 점검 발동 임계치 |
| `LOCAL_GATES` | 해당 저장소 전용 검사 활성화 목록 |

> 설정과 실제 구조가 불일치할 경우 배치 검사가 이를 검출합니다. 선언되지 않은 폴더에 애플리케이션 코드를 생성하면 저장 시점에 차단되며, 설치 스크립트도 선언 외 코드 폴더를 1회 보고합니다.

### 5.4 모델 역할 분담

작업 성격에 따라 모델 등급을 분리하여 실행합니다. 이 배정 또한 검사 대상이며, 정책표와 에이전트 정의가 불일치하면 세션이 종료되지 않습니다.

| 모델 | 담당 | 배정 기준 |
|:--|:--|:--|
| **Opus** | 아키텍처 설계, 판단, 검수 | 되돌리기 비용이 높은 판단. 등급 하향 없음 |
| **Fable** | 승인된 설계서의 전체 구현 | 판단이 종료되고 작업량만 남은 단계. 설계서에 미확정 항목이 있으면 중단 후 반려 |
| **Sonnet** | 다중 파일 정독 및 대조 | 판단 폭이 좁고 처리량이 큰 작업. 요약만 반환 |

## 6. 유지보수 및 검사 확장

### 6.1 기존 프로젝트 도입

레거시 코드가 존재하는 프로젝트에 도입할 경우 첫 검사에서 다수의 위반이 검출될 수 있습니다. 이 상태를 방치하면 검사 자체를 비활성화하게 되므로, 설치 스크립트는 **도입 시점의 기존 위반을 사전 등록하여 예외 처리**합니다.

| 대상 | 처리 |
|:--|:--|
| 도입 시점에 이미 존재하던 위반 | `(검사 항목, 파일)` 단위로 등록. 검사에서 제외 |
| 등록된 파일을 이후 수정할 때 | 위반을 수정하고 등록 항목을 삭제 |
| 신규 생성 파일 | 예외 없이 전 검사 통과 필수 |

등록 목록은 감소만 허용됩니다. 수정 완료된 항목은 다음 명령으로 일괄 정리합니다.

```bash
python -X utf8 harness_install.py --dry-run   # 등록 예정 항목 확인
python -X utf8 harness_install.py --prune     # 수정 완료 항목 정리
```

생성된 등록 파일은 커밋합니다. 세션 및 작업 환경이 변경되어도 상태가 공유되어야 목록의 단조 감소가 성립합니다.

### 6.2 검사 규칙 추가 프로세스

장애 또는 작업 실수 발생 시 다음 절차로 규칙을 추가합니다.

| 단계 | 수행 | 산출물 |
|:--:|:--|:--|
| 1 | 사고 경위와 손실 내용을 기록합니다. 규칙만 기재하면 다음 세션이 예외로 판단할 여지가 있으므로 대가를 함께 기록합니다 | `dev/LESSONS.md` |
| 2 | 기계적 검출 가능 여부를 판정합니다 | — |
| 3 | 검출 가능한 경우 검사로 구현합니다. 범용 규칙은 `kernel/`, 해당 저장소 전용 규칙은 `harness_gates/`에 배치합니다 | 검사 모듈 |
| 4 | 검출 불가능한 경우 `산문 전용`과 사유를 명시합니다 | `dev/LESSONS.md` |

3단계와 4단계 중 어느 것도 기재하지 않으면 검사가 이를 검출합니다. 판단을 보류한 상태이기 때문입니다. 결과적으로 산문 전용으로 분류된 목록이 다음 검사 구현 후보가 됩니다.

### 6.3 정기 점검

프로젝트 규모가 증가하면 문서와 코드의 불일치, 과설계, 미처리 부채가 누적됩니다. 본 도구는 저장소 실물에서 임계치를 측정하여 점검 시점을 자체 판단하며, 별도의 명령 입력을 요구하지 않습니다.

| 점검 항목 | 측정 기준 |
|:--|:--|
| 문서·코드 불일치 | 최종 실행 이후 커밋 수 또는 경과일 |
| 과설계 및 복잡도 | 최종 실행 이후 커밋 수 또는 경과일 |
| 미처리 부채 | 소스 내 잔존 표시 개수 |
| 화면 사용성 | 화면 파일 변경 건수 |
| 사용자 관점 검수 | 화면 파일 변경 건수 |

임계치 초과 시 세션 시작 단계에서 보고되며, 진행 중인 작업 완료 후 자동 실행됩니다. 모든 점검은 보고서만 생성하고 소스를 변경하지 않으므로 별도 승인을 요구하지 않습니다. 화면 레이어가 없는 프로젝트에서는 관련 2개 항목이 보고 대상에서 제외됩니다.

임계치 조정은 `harness_profile.py`의 `MAINTENANCE` 항목에서 수행합니다.

### 6.4 검사기 자체 검증

검사기 수정 시 특정 검사가 무력화되는 회귀를 방지하기 위해, 검사 항목별 위반을 1건씩 배치한 픽스처와 그 검사 결과 정답지를 보유합니다.

```bash
python -X utf8 tests/run_golden.py          # 전체 설정 기준 대조
python -X utf8 tests/run_golden.py --bare   # 설정 부재 기준 대조
```

현재 출력과 정답지를 대조하여 차이가 발생한 행을 보고합니다. 검사기 리팩터링 시 이 대조가 통과 기준이 됩니다.

## 7. 자주 묻는 질문

**기술 스택을 결정하지 못한 상태에서도 설치가 가능합니까?**
가능합니다. 온보딩은 기술명이 아닌 결과물의 형태를 질의합니다. 미정을 선택할 경우 가장 보편적인 구성으로 설치되며, 사용하지 않는 영역의 검사는 비활성 상태로 유지됩니다.

**설치 이후 프로젝트 성격이 변경되면 어떻게 합니까?**
`harness_profile.py`의 해당 항목을 수정합니다. 화면 없이 시작한 프로젝트에 화면을 추가하는 경우 `LAYERS["ui"]` 한 항목을 기입하면 화면 관련 검사 7종이 대상 수집을 시작합니다. 그중 화면 금칙어와 브라우저 API 래퍼 2종은 추가 설정을 요구합니다.

**특정 검사가 프로젝트에 부적합한 경우 비활성화가 가능합니까?**
해당 설정 항목을 비우면 `[SKIP]` 상태로 전환됩니다. 다만 비활성 사실은 매 실행 시 사유와 함께 출력되며, 이를 숨기는 설정은 제공하지 않습니다.

**개발자가 직접 작성해야 하는 내용은 무엇입니까?**
설치 시점에는 없습니다. 폴더명 및 프레임워크 함수명은 온보딩 절차가 처리합니다. 개발자만 보유한 정보는 해당 서비스가 속한 도메인 지식이며 `PROJECT.md`에 기재합니다. 취급 대상, 사용 용어, 유효 수치 범위 등이 이에 해당하며, 사전 일괄 작성이 아닌 개발 진행에 따라 누적됩니다.

**GitHub 저장소를 사전에 생성해야 합니까?**
`gh` 인증이 완료된 상태라면 비공개 저장소를 자동 생성하고 푸시합니다. 저장소명은 디렉토리명을 사용합니다. 공개 저장소는 되돌리기 어려운 작업이므로 명시적 요청이 있을 때만 생성합니다. 인증이 없는 경우에만 저장소 주소를 질의합니다.

**모바일 앱으로 확장할 계획이 있는 경우 사전 준비가 필요합니까?**

<details>
<summary>화면을 포함하는 프로젝트의 앱 이식 대비 규칙</summary>

현재 개발 기준은 웹입니다. 다만 앱 이식 시 재사용 대상과 폐기 대상이 사전에 구분되므로, 재사용 대상을 초기부터 분리합니다.

| 규칙 | 이식 시 처리 |
|:--|:--|
| 계산 및 데이터 가공을 화면 파일 외부에 배치 | 로직 그대로 이동 |
| 색상·간격·글자 크기를 정본 파일에서만 참조 | 값 그대로 재사용 |
| 브라우저 전용 기능은 단일 래퍼 경유 | 해당 파일만 교체 |
| 페이지 이동 코드를 페이지 계층에 한정 | 교체 범위 최소화 |

앱 개발이 필요해질 경우 화면 계층만 재구현하며 서버·로직·디자인 값은 이관됩니다. 앱을 개발하지 않더라도 손실은 없습니다. 이 분리는 그 자체로 유효한 구조이기 때문입니다.

화면은 설계 단계에서 데스크톱과 모바일 배치를 함께 확정한 경우에만 승인됩니다.
