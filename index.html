이 레포는 나를 어떻게 붙잡아 두는가

fund_monitor의 하네스는 "잘 하자"는 산문이 아니라, 세션의 정해진 순간에 실제로 프로세스를 띄워 판정하고 진행을 막는 기계다. 이 문서는 그 기계가 언제·무엇을·어떻게 판정하는지를 단계별로 푼다. 모든 서술은 .claude/settings.json·훅 스크립트 7개·static_check.py 계열 14개 모듈을 직접 읽고 실행해 확인했다.

작성 2026-08-04 훅 7 게이트 섹션 35 에이전트 5 스킬 13 정본 코드 · 이 문서는 사람용 해설

00한 장 요약

하네스는 세 층이다. 위층은 사람이 읽는 규칙, 가운데는 그 규칙을 발화시키는 배선, 아래층은 기계가 판정하는 검사다. 층이 내려갈수록 강제력이 세진다.

① 규칙*.md
산문 규칙. CLAUDE.md가 진입점이고 작업 종류별로 읽을 MD를 라우팅한다. 강제력은 0 — 세션이 길어지면 흘러내린다. 그래서 이 층은 검사 불가능한 것만 담는 게 원칙이다.
② 배선.claude/
훅 등록. .claude/settings.json이 "어떤 이벤트에 어떤 커맨드를 실행할지"를 선언한다. 훅은 Claude가 아니라 런타임이 실행하므로 내가 잊거나 건너뛸 수 없다.
③ 판정static_check*.py
정적 검사기. 25개 번호의 규칙을 코드로 판정한다. 위반이 있으면 exit 1, 그걸 받은 훅이 exit 2로 세션 종료 자체를 막는다.
설계 의도 한 줄 검사 가능한 규칙을 MD 산문으로 단속하는 것 자체가 실패 메커니즘이다. 그래서 새 규칙이 기계로 검사 가능하면 MD에 문장을 더하는 게 아니라 static_check.py에 검사를 더한다.

01세션 타임라인

세션이 시작해서 끝날 때까지 훅이 발화하는 순서다. 빨간 점은 진행을 막을 수 있는 지점이다.

SessionStart
세션 열림 — 커맨드 3개가 순서대로 실행된다. ① lazy-persona.md를 통째로 출력해 내 컨텍스트에 주입 ② node --version으로 impeccable UI 훅 생존 확인 ③ git_staleness.py가 공유 체크아웃이 origin/main보다 뒤졌는지 검사
UserPromptSubmit
사용자가 프롬프트를 보낼 때마다 — check_context_growth.py transcript 파일 크기가 15MB를 넘으면 경고를 띄우고 /clear를 권고한다. 차단은 하지 않는다 — 세션 분리는 사용자 결정이다.
PreToolUse · Read
내가 파일을 읽기 직전 — check_context_diet.py 추정 16,000토큰이 넘는 파일을 limit 없이 통으로 읽으려 하면 여기서 잘린다. 툴이 실행되기 전에 막히므로 컨텍스트가 오염되지 않는다.
PostToolUse · Edit / Write / MultiEdit
파일을 저장한 직후 — check_file_rules.py + impeccable hook.mjs 레거시 UI 경로면 즉시 차단. 그 외 .py·.ts·.tsx·.md는 방금 저장한 그 파일만 static_check.py --file로 검사한다. 위반이면 그 턴 안에 고치라는 피드백이 돌아온다.
SubagentStop
서브에이전트가 반환하려 할 때 — check_agent_return.py 최종 반환문이 20,000자를 넘으면 종료를 막는다. 그 반환은 통째로 메인 루프에 얹혀 남은 세션 내내 재전송되기 때문이다.
Stop
내가 턴을 끝내려 할 때 — check_editing_lock.py → check_coding_rules.py ① EDITING.md 과업 보드에 내 #sid 행이 남아 있으면 차단 ② static_check.py 전체 검사에 위반이 하나라도 있으면 차단. 둘 다 통과해야 세션이 끝난다.
읽는 법 같은 규칙이 두 번 걸린다. PostToolUse는 "쓰는 순간", Stop은 "끝내는 순간". 앞의 것은 잔 리팩토링이 쌓이는 걸 막고, 뒤의 것은 앞의 것을 우회한 경로(Bash 리다이렉트 등)를 마지막에 잡는다.

02훅 계약 — exit 코드와 출력 채널

훅이 런타임과 주고받는 규약은 단순하다. 이걸 알면 훅 코드를 읽을 때 판정 결과가 바로 보인다.

신호의미내가 받는 것
exit 0통과아무것도 없음 — 조용히 진행
exit 2 + stderr차단stderr 내용이 그대로 나에게 전달된다. stdout은 무시된다 — 그래서 모든 차단 훅이 file=sys.stderr로 출력한다
exit 0 + JSON stdout비차단 주입systemMessage는 사용자 화면에, additionalContext는 내 컨텍스트에. check_context_growth.py만 이 방식을 쓴다
stdin JSON훅 입력훅은 tool_input.file_path·session_id·transcript_path·stop_hook_active를 여기서 읽는다

fail-open과 fail-closed — 훅이 자기 판단을 못 할 때

훅 자신이 고장났을 때 통과시킬지 막을지는 훅마다 다르게 정해져 있다. 기준은 "틀렸을 때 어느 쪽이 덜 위험한가"다.

훅고장 상황선택이유
check_file_rules페이로드 파싱 실패 / 검사 30초 무응답fail-closed검사 대상조차 모르는 상태다. 조용히 통과시키면 규칙 위반 코드가 그대로 남는다
check_editing_locksession_id를 못 읽음fail-closed내 행인지 남의 행인지 구분 불가 — 전 행을 차단해 완료 보고를 강제한다
check_agent_return반환문을 못 찾음fail-open페이로드 스키마가 버전마다 달라질 수 있다. 전 에이전트가 종료 못 하는 쪽이 더 위험하다
check_context_diet페이로드·파일 읽기 실패fail-open읽기 자체를 막으면 세션이 아무 일도 못 한다
git_staleness오프라인·인증 실패·타임아웃fail-open세션 시작을 막을 이유가 없다. 조용히 통과한다

03훅 7종 해부

각 훅의 정확한 판정식이다. 임계값의 정본은 코드이고, 여기엔 왜 그 값인지를 함께 적었다. 파일별 원문 배선과 상수는 훅 레퍼런스에 있다.

lazy-persona 주입 비차단

.claude/hooks/lazy-persona.md · SessionStart · timeout 10s

파일을 print()로 통째로 출력하는 것뿐이다. SessionStart 훅의 stdout은 내 컨텍스트에 주입되므로, 결과적으로 매 세션 첫 줄부터 "lazy 시니어 개발자" 페르소나 — 사다리(YAGNI → 기존 코드 재사용 → 표준 라이브러리 → …)와 게으르면 안 되는 경계(입력 검증·에러 처리·보안·접근성)가 내 안에 들어와 있다.

check_editing_lock.py 차단 fail-closed

.claude/hooks/check_editing_lock.py · Stop

EDITING.md의 Active Edits 표를 파싱해 이 세션이 등록한 과업 행이 남아 있으면 종료를 막는다. = 머지까지 끝내고 행을 지우는 완료 보고를 강제하는 장치다.

행의 상태판정이유
내 #sid:xxxxxxxx가 붙은 행차단내가 해제하지 않은 잠금
다른 sid 행 · 태그 없는 행통과다른 세션이 작업 중일 수 있다
세션 ID를 못 읽음전 행 차단구분 불가 시 안전한 쪽

#sid는 내 scratchpad 경로 UUID의 앞 8자다. 이 태그 체계는 사고의 산물이다 — 구버전은 잠금 행 전체를 차단해서, 다른 세션이 작업 중이면 이 세션이 영원히 종료 못 하는 데드락이 났다.

파서는 HTML 주석 블록·표 헤더·구분선을 건너뛴다. 그래서 EDITING.md 안의 예시 행은 잠금으로 세지 않는다.

check_coding_rules.py 차단

.claude/hooks/check_coding_rules.py · Stop

가장 단순하고 가장 센 훅이다. static_check.py를 인자 없이 실행해 전체 검사를 돌리고, exit 1이면 위반 목록을 stderr로 뱉으며 종료를 막는다. 내가 고친 뒤에야 세션이 끝나므로, 사용자에게는 통과한 최종물만 올라간다.

자식 프로세스를 -X utf8로 띄우는 건 장식이 아니다. Windows 기본 cp949 출력이 부모의 utf-8 디코드에서 깨져 한글 위반 메시지가 통째로 유실된 적이 있다. 같은 이유로 모든 훅이 sys.stderr.reconfigure(encoding="utf-8")로 시작한다.

.md⑬ 스타일 + ④A~④E·⑯ 전역 교차검사전역 검사는 .claude/·docs/ 하위 MD 편집일 때는 생략
그 외 확장자없음.html·.json·.css·.sql
MD를 고치면 레포 전체가 검사된다 정본 MD 한 줄을 고쳐도 ④A~④E가 통째로 돈다. MD 참조 경로 실존, 배치 스케줄 표와 코드 상수, .env 키 목록, 고아 MD, 하네스 지도 대조까지 전부. MD 편집이 가장 비싼 편집인 이유이자, MD와 코드의 드리프트가 자동으로 잡히는 이유다.

출력 등급 — [OK] · [FAIL] · [REPORT]

등급의미총계 합산
[OK]해당 섹션 위반 0—
[FAIL]강제 위반 — 건수와 위치를 나열합산 → exit 1
[REPORT]MD 스타일 게이트 ⑬의 연성 신호 (날짜 태그·경로 토큰·시그니처 밀도)합산 안 함 — 차단하지 않는다

⑬의 연성 항목이 차단하지 않는 이유는 오탐 여지 때문이다. "이 줄이 성분 A·C의 재유입 신호"라는 건 기계가 힌트만 줄 수 있고, 최종 판정은 월 1회 /md-audit이 사람 판단으로 한다.

06예외 3종과 래칫

게이트를 통과 못 하는 정당한 코드는 있다. 예외를 어떻게 주느냐가 하네스의 수명을 결정한다.

① allowlist 파일

파일 단위 영구 면제. 게이트 도입 시점의 기존 실태를 담는다.

실물: md_ref_allowlist.txt, 모듈 안의 ANY_ALLOWLIST·HEX_ALLOWLIST·ROSTER_ALLOWLIST 등

② 인라인 주석

줄 단위 예외. 사유를 같이 쓴다. 신규 코드는 allowlist 등재 대신 이쪽을 쓰는 게 원칙이다.

실물: # any-ok: 사유 · // any-ok: 사유

③ baseline 래칫

기존 위반을 동결하고 증가만 막는다. 파일에서 줄을 지우는 방향으로만 수정 가능하다.

실물: static_check_tests_baseline.txt · static_check_schema_baseline.txt · static_check_api_array_baseline.txt + 모듈 안 BASELINE 상수

래칫 원칙 대규모 정리는 그 상태를 잠그는 검사와 같은 커밋으로 끝낸다. 게이트 없는 정리는 재발한다 — 실제로 게이트 ④A~④E가 활성화된 시점이 대규모 MD 정리 완료 커밋이다.
현재 실측 상태 (2026-08-04) MD 스타일 게이트 ⑬의 유예 파일 static_check_md_baseline.txt는 레포에 존재하지 않는다. 코드는 파일이 없으면 빈 집합으로 처리하므로 — 유예 대상이 하나도 없고 전 MD가 강제 검사를 받는 상태다. 래칫이 끝까지 감겨 있다.

07자기검사 루프 — 하네스가 하네스를 감시한다

이 구조에서 제일 재미있는 부분이다. 하네스를 바꾸면 하네스 문서도 같이 바뀌어야 하고, 그걸 게이트가 확인한다.

④E는 한 방향만 본다 실물 → 지도 방향이다. 실물에 있는데 지도에 없으면 잡히지만, 지도에만 남은 유령 항목은 안 잡힌다. 또 이름의 존재만 확인하고 서술 내용은 검사하지 않는다 — 실제로 HARNESS.md의 PostToolUse 행은 매처를 Edit·Write로 적고 있지만 settings.json의 실제 매처는 Edit|Write|MultiEdit다. 이런 종류의 드리프트는 게이트가 아니라 월 1회 /md-audit이 잡는 몫이다.

같은 패턴의 다른 자기검사

  • ④D 고아 MD — 새 MD를 만들고 허브 라우팅표에 등재하지 않으면 잡힌다. 문서가 존재하는데 읽힐 경로가 없는 상태를 막는다.
  • ④B 배치 스케줄 — batch_runner.py의 실행 시각 상수를 바꾸고 DEVGUIDE.md 표를 안 고치면 잡힌다.
  • ④C .env 키 — 양방향이다. 코드에만 있어도, 문서에만 있어도 잡힌다.

10규칙을 새로 넣을 때

판단 기준 하나로 갈린다 — 기계가 검사할 수 있는가.

검사 가능하다

  1. static_check*.py에 검사 함수를 추가한다
  2. _build_sections()에 섹션 한 줄로 등록한다
  3. 기존 위반이 많으면 baseline으로 동결하고 같은 커밋에서 잠근다
  4. HARNESS.md 게이트 표에 행을 추가한다

MD에 문장을 더하는 것은 이 경우 틀린 대응이다.

검사 불가능하다

  1. 해당 정본 MD에 한 사실 한 곳 원칙으로 적는다
  2. 새 MD를 만들었으면 같은 턴에 허브 라우팅표에 등재한다 (안 하면 ④D가 잡는다)
  3. 산문 드리프트는 월 1회 /md-audit이 상한선이다

훅을 새로 붙일 때 주의점

  • 훅 command는 상대경로로 등록한다. %CLAUDE_PROJECT_DIR% cmd 표기는 이 환경에서 확장되지 않아 훅이 통째로 실패한다. cwd는 프로젝트 루트가 보장된다.
  • 차단 사유는 반드시 stderr로 낸다. stdout은 무시된다.
  • Windows 콘솔 인코딩 때문에 sys.stderr.reconfigure(encoding="utf-8")와 자식 프로세스 -X utf8이 사실상 필수다.
  • 같은 턴에 HARNESS.md를 갱신한다. 안 하면 ④E가 다음 검사에서 막는다.
