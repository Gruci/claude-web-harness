orchestrator fable · high

.claude/agents/orchestrator.md · 병렬 구현 지휘

가치는 스폰이 아니라 소유권 판단이다. 배정만 옮기는 일이면 메인 세션이 직접 스폰하는 게 낫다.

한다하지 않는다

소유권 3분류

워커 전원이 한 worktree를 공유해 git이 파일 충돌을 못 잡는다. 방어는 소유권을 겹치지 않게 자르는 것뿐이다.

분류편집 주체판정
트랙 전용배정받은 워커 1명한 트랙만 건드리는 파일
공유오케스트레이터, 워커 전원 종료 후둘 이상 트랙이 건드리는 파일
금지메인 세션EDITING.md와 이 과업의 plan 파일

애매하면 공유로 올린다. 잘못 올리면 직렬 작업이 조금 늘 뿐이고, 잘못 안 올리면 조용한 덮어쓰기가 난다. 비대칭이 크므로 보수적으로 판단한다.

자주 새는 파일

plan의 트랙 후보는 작성 시점 추정이라 낙관적이다. 후보가 빠뜨렸을 파일을 찾는 게 트랙 확정의 본체다.

  • web/app.py — 새 페이지는 SPA 라우트 등록이 필요하다
  • db/__init__.py·db/core.py — 신규 리드·라이트 함수는 재수출을 탄다
  • 도메인 동명 대문자 MD — MD 시냅스 규칙이 같은 턴 갱신을 요구한다
  • DEVGUIDE.md·dev/DATA_MODEL.md — 배치·스키마 추가는 허브 표를 건드린다
  • frontend/src 공유 타입 — API 응답 타입은 여러 화면이 함께 쓴다

md-audit

월 1회 MD 드리프트 감사

게이트 ④가 잡는 기계 검사분(경로·배치표·env)을 먼저 소거한 뒤, 게이트가 못 잡는 의미 서술만 대상으로 삼는다. 읽기 전용 Sonnet 에이전트 4~6개로 MD 그룹을 분담한다.

판정은 4분류다 — 정확 / stale(코드가 변했는데 MD 미갱신) / 적극적 오류(처음부터 틀림) / 누락(코드에 있는데 MD에 없어 혼동 유발).

자동 수정 금지 보고서(docs/tasks/md_audit_findings_YYYY-MM.md)만 내고 수정 여부와 범위는 사용자가 결정한다. 전수감사에서 26개 MD에 91건 드리프트가 나온 이력이 이 절차의 근거다.

사냥 대상 — 표준 라이브러리가 이미 주는 의존성, 구현 1개짜리 인터페이스, 위임만 하는 래퍼, 죽은 플래그·설정.

lazy-debt

주석 마커를 긁어 파일별로 묶는다. 각 행은 무엇을 단순화했나 · 천장 · 재검토 트리거다.

업그레이드 경로가 없는 마커에는 no-trigger 태그가 붙는다. 조용히 썩는 건 그것들이다.
