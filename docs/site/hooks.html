lazy-persona 본문

SessionStart마다 통째로 주입되는 파일이다. 다른 훅과 달리 판정하지 않고 행동 규칙을 심는다.

단사다리 — 먼저 걸리는 칸에서 멈춘다
1애초에 존재할 필요가 있나. 추측성 수요면 건너뛰고 한 줄로 밝힌다
2이 코드베이스에 이미 있나. 헬퍼·유틸·타입·패턴이 있으면 재사용한다
3표준 라이브러리가 하나
4플랫폼 기본 기능으로 되나. CSS가 JS보다, DB 제약이 앱 코드보다 낫다
5이미 설치된 의존성으로 되나. 몇 줄이면 될 일에 새 의존성을 넣지 않는다
6한 줄로 되나
7그제서야 — 동작하는 최소 코드

게으르면 안 되는 경계

  • 신뢰 경계의 입력 검증, 데이터 유실을 막는 에러 처리, 보안, 접근성 기본, 명시적으로 요청된 것은 단순화 대상이 아니다.
  • 문제 이해에는 게으르지 않는다. 사다리는 해답을 짧게 만들지, 읽기를 짧게 만들지 않는다.
  • 버그 수정은 증상이 아니라 근본 원인. 공용 함수 한 곳의 가드가 호출부마다 넣는 가드보다 작은 diff다.
  • 실제 천장이 있는 의도적 단순화에는 lazy: 주석으로 천장과 업그레이드 경로를 남긴다. 그 마커를 /lazy-debt가 수확한다.
  • 사소하지 않은 로직은 깨지면 실패하는 검사 하나를 남긴다. 프레임워크·픽스처는 요청 없으면 안 만든다.
서브에이전트에는 주입되지 않는다 SessionStart는 메인 세션에만 발화한다. 그래서 orchestrator가 워커를 스폰할 때 ".claude/hooks/lazy-persona.md를 먼저 Read하라"를 프롬프트 필수 항목으로 못박아 뒀다. 빠뜨리면 워커가 사다리 없이 과설계한다.

훅 작성 규약

7개 파일에 공통으로 박혀 있는 패턴이다. 새 훅을 붙일 때 그대로 따른다.

규약코드안 지키면
차단 사유는 stderrprint(..., file=sys.stderr)stdout은 무시돼 이유 없이 막힌 것처럼 보인다
stderr utf-8 재설정sys.stderr.reconfigure(encoding="utf-8")Windows cp949에서 한글 메시지가 깨진다
자식 프로세스 utf-8[sys.executable, "-X", "utf8", ...]부모의 utf-8 디코드가 실패해 출력이 통째로 유실된다
레포 루트 해석Path(__file__).resolve().parents[2]cwd에 의존하면 worktree에서 어긋난다
커맨드는 상대경로python .claude/hooks/x.py%CLAUDE_PROJECT_DIR%가 이 환경에서 확장되지 않아 훅이 통째로 실패한다
fail 방향 명시except → exit 0 또는 exit 2고장 시 동작이 우연에 맡겨진다

등록되지 않은 이벤트

있는 것만큼 없는 것도 사양이다. 아래는 이 레포가 쓰지 않는 지점이라, 여기에 기대는 규칙은 강제되지 않는다.

이벤트상태결과
PreToolUse(Edit·Write)미등록레거시 경로 쓰기는 사후 차단이라 파일이 이미 만들어진다. 되돌리는 건 내 몫
PreToolUse(Bash)미등록Bash 리다이렉트로 파일을 만들면 작성 시점 게이트를 통째로 건너뛴다. 산문 규칙으로만 금지된다
PostToolUse(Read·Grep·Glob)미등록읽기 결과에는 사후 검사가 없다
Notification미등록알림 훅 없음
가장 큰 구멍 Bash로 소스를 생성·수정하면 PostToolUse 게이트가 발화하지 않는다. Stop 훅의 전체 검사가 마지막 방어선이지만, 그때는 이미 세션 끝이라 수정 비용이 커진다. 그래서 "소스 생성·수정은 반드시 Edit/Write"가 CLAUDE.md의 명시 규칙이다.
