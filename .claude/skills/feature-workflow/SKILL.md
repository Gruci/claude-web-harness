# feature-workflow — 4단계 기능 개발

> **모델 배분**: 1단계 리서치·2단계 계획은 메인 루프(Opus 5)가 직접 수행 — 서브 에이전트 위임 금지. 3단계 구현을 위임할 땐 model을 지정하지 않는다. 각 에이전트 frontmatter가 정본이다 (CLAUDE.md 모델 라우팅).

## Phase 0: 컨텍스트 확인 + 범위 인터뷰

1. `docs/tasks/`에 research.md/plan.md가 있는지 확인:
   - 있음 + 부분 수정 요청 → **부분 재실행** (기존 산출물 읽고 해당 단계만)
   - 있음 + 새 기능 요청 → 미완료 작업 경고 후 archive 처리 확인
   - 없음 → 초기 실행
2. **범위 인터뷰**: 리서치 시작 전에, 구현 시 정해져야 하는 결정 지점(스코프 경계·데이터 적재 방식·화면 노출 위치 등)을 추려 AskUserQuestion으로 먼저 묻는다. 답을 전제로 research/plan을 작성한다. 물어볼 게 진짜 없는 자명한 작업만 생략.

## 📍 1단계: 리서치

```
관련 파일들을 매우 깊이 읽고 현재 시스템이 어떻게 동작하는지 완벽하게 이해해라.
표면적으로 파일명이나 함수 시그니처만 훑지 말고,
내부 로직·데이터 흐름·다른 모듈과의 의존성까지 모든 세부 사항을 파악해라.

절대로 채팅창 안에서 구두로 요약해서 답변하지 마라.
발견한 내용과 현재 시스템의 작동 방식을 매우 상세히 담은
`docs/tasks/research.md` 파일을 작성해라.

이 단계에서 소스 파일은 절대 수정하지 마라.
```

## 📍 2단계: 계획

```
research.md를 바탕으로 상세한 `docs/tasks/plan.md`를 작성해라.

포함 내용:
- 접근 방식 상세 설명
- 변경/추가될 실제 코드 스니펫 (실제 코드베이스 문맥 100% 반영 — 추상적 계획 금지)
- 수정될 파일의 정확한 경로
- **파일 설계표**: 신규·수정 파일별 | 경로 | 단일 책임 1줄 | 예상 규모 | — 400줄 근접이 예상되면 plan에서 미리 분할 설계 (사후 분할 리팩토링 방지)
- **반응형 설계표** (화면 작업 포함 시): 화면·컴포넌트별 | 데스크톱 배치 | 모바일 배치 | 전환 방식 | — `design/RESPONSIVE.md` 기준. 모바일 배치를 정하지 않은 화면 plan은 미완성
- 브레이킹 체인지·트레이드오프

plan.md 작성이 끝나면 대기해라.
사용자가 검토하고 승인하기 전까지 절대로 실제 코드 구현을 시작하지 마라.
```

## 📍 2-1단계: 계획 검토·수정 반복

사용자가 plan.md에 메모/주석을 추가하면 → 모든 메모의 의도와 제약을 반영해 plan.md를 업데이트하고 다시 대기. 만족할 때까지 반복.

## 📍 3단계: 구현

**착수 전 규모 판정** — plan 파일 설계표 기준으로 실행 주체를 정한다.

| 규모 | 실행 |
|------|------|
| 파일 8개 이상 또는 레이어 3개 이상 횡단 | `executor` 에이전트에 plan을 통째로 위임 |
| 그 외 | 메인 루프 직접, 또는 backend·frontend |

executor 브리프에는 목표와 범위 밖 항목과 plan 경로만 넣는다. **아래 절차 블록을 그대로 넘기지 않는다** — 단계 나열은 장기 자율 실행 품질을 떨어뜨린다 (`CLAUDE.md` 모델 라우팅). 브리프는 plan이 No-Placeholder임을 전제한다 — plan에 미정의 참조·TBD가 있으면 위임 전에 메인 루프가 메운다. executor(Fable)는 그 갭을 판단으로 메우지 않고 반환한다.

```
plan.md와 Todo 리스트를 바탕으로 전부 구현해라.

- EDITING.md 잠금 프로토콜 준수 (편집 전 등록 → 편집 → 해제).
- 신규 파일 작성 전 dev/CONVENTIONS.md + golden exemplar Read 후 모방.
- 작업 완료할 때마다 plan.md에서 완료로 표시해라.
- 모든 작업이 완료될 때까지 멈추지 말고 계속 진행해라.
- `Any`/`unknown` 타입 남발 금지.
- 지속적으로 typecheck·pytest·게이트를 실행하고 검증해라.
- 코드 변경 완료된 그 턴 안에 관련 MD 업데이트까지 끝내라.
```

## 📍 4단계: 수정/롤백

**부분 수정 시:** "다른 곳은 건드리지 말고 이 부분만 빠르고 정확하게 수정" — 외과적 변경.
**전면 롤백 시:** git restore/reset으로 전부 되돌린 후, 지정된 좁은 기능만 가장 심플하게 재작성. 지정한 것 외엔 아무것도 변경 금지.

## 완료 후 정리 (그 턴 안에 즉시)

1. **`/lazy-review` 자동 실행** — 이번 diff의 과잉설계 검토. 발견 항목 중 이번 작업 범위 내 것은 그 자리에서 삭제·단순화 후 재검증 (범위 밖 기존 코드는 보고만).
2. archive 이동:

```bash
mkdir docs/tasks/archive/YYYY-MM-DD-{작업명}
git mv docs/tasks/research.md docs/tasks/archive/YYYY-MM-DD-{작업명}/
git mv docs/tasks/plan.md     docs/tasks/archive/YYYY-MM-DD-{작업명}/
```

## 테스트 시나리오

- 정상: "대시보드에 요약 카드 추가해줘" → Phase 0 인터뷰(카드 항목·위치) → research.md → plan.md → 승인 대기 → 구현 → archive
- 에러: plan 승인 전 사용자가 "그냥 빨리 해줘" → 오탈자급이 아니면 절차 유지 이유를 설명하고 최소한 plan 요약 승인을 받는다
